| **核心信息（一句话）** | 丢帧、时钟漂移、分辨率低、DBC 不全、单位不统一、信号缺失，六类问题各有工程解法。 |
| **页面要素** | 六行三列表格（问题 / 影响 / 应对）：丢帧与总线负载抖动 → 信号时间轴有洞 → 质量评分 + 插值/物理模型补全；时间戳漂移 → 多源无法对齐 → 与 GNSS UTC 对齐，估计并补偿时钟偏置；信号分辨率低（如 `TotalFuelUsed` **步进 0.5 L**）→ 短行程对账误差大 → 长窗口对账 + 多信号交叉验证；DBC 不完整/保密 → 部分信号解不出 → J1939 标准 PGN 反查 + 逆向解析 + 物理量反推；单位与符号约定不统一 → 算出负数/量级错误 → 单位注册表 + 量纲断言 + 自动异常告警；信号缺失（低配车型）→ 关键量算不出 → 冗余估计（扭矩法、RLS 质量辨识、卡尔曼坡度融合）。 |
| **口播要点（45 秒）** | 我想先承认一件事：**真实报文是脏的**。丢帧、时间戳漂移、`TotalFuelUsed` 这种信号步进是 0.5 升，短行程根本对不准；DBC 还经常不全，甚至保密。我们的态度是不打滤镜——每一类问题在方案里都有对应的工程解法：丢帧用质量评分加物理模型补全，时钟漂移拿 GNSS 的 UTC 当基准去估偏置，分辨率不够就用**长窗口对账**，DBC 拿不到就走 J1939 标准 PGN 反查再逆向。而且每车每天会输出一个 0 到 100 的**质量分**，分低的数据我们自动标注"结论置信度低"，**宁可不说，也不输出误导结论**。 |

### 第 7 页 · 能耗物理模型：能量瀑布图（本方案的技术内核）

| 项 | 内容 |
|---|---|
| **标题** | 一个数字变成一堆分项：能量瀑布 |
| **核心信息（一句话）** | `E_chem = E_idle + E_aux + E_roll + E_aero + E_grade + E_kinetic + E_brake + E_dt_loss + ε`，各项之和必须回到总量，ε 应小于 5%。 |
| **页面要素** | 中央大幅**瀑布图**（从总化学能/电能逐级扣减：怠速耗能、附件、滚动阻力、空气阻力、坡道（上坡为正，下坡回收为负）、净加速（可正可负）、制动耗散、传动损失，末端留残差 ε）；左侧公式区：`E_fuel[L] = ∫ EngineFuelRate dt / 3600`，`E_chem[kWh] = E_fuel × 9.99`（LHV 42.8 MJ/kg、密度 0.84 kg/L → 35.95 MJ/L ≈ **9.99 kWh/L**）；电动车 `P_batt = U·I/1000`、`E_batt = ∫P_batt dt`；右侧纵向动力学区：`F_total = m_eff·a + m·g·sinθ + m·g·C_rr·cosθ + ½·ρ·C_d·A·(v+v_wind)²`，`P_wheel = F_total·v`，`P_engine = P_wheel/η_drivetrain + P_aux`。底部一行为难点三解法：质量未知→轴荷传感器/RLS 辨识；坡度未知→GNSS 海拔差分/气压高度计/卡尔曼融合；风速未知→按 `v_wind=0` 并用长期巡航段反标 `C_d·A`。 |
| **口播要点（60 秒）** | 这一页是整个方案的技术内核。能耗这件事，其实物理规律非常明确：燃油的化学能，最后只去了几个地方——**怠速烧掉一部分，空调加热这类附件拿一部分，滚动阻力、空气阻力、坡道、加速动能、制动耗散，再加上传动损失**。我们把这九项逐项算出来，画成这张**能量瀑布图**。燃油侧我们按低热值 42.8 兆焦每公斤、密度 0.84 换算，一升柴油约等于 **9.99 度电**，这个换算让油和电可以在同一张图上比较。电动车就是电压乘电流积分。这里有三个工程难点必须解决：**整车质量不知道**，有轴荷传感器就直接读，没有就用递推最小二乘在加速段辨识；**坡度不知道**，用 GNSS 海拔差分加卡尔曼滤波平滑；**风速没有传感器**，我们就按零风速处理，再用长期巡航数据反标空气阻力系数，把系统偏差吸收进去，不引入不可观测的变量。最后注意瀑布图末尾这一项 **ε，残差，它必须小于 5%**——超了就说明模型或数据有问题。 |

### 第 8 页 · 三道自检：让结论"敢拿去对账"

| 项 | 内容 |
|---|---|
| **标题** | 三道自检不通过，报告不许发布 |
| **核心信息（一句话）** | 能量守恒 < 3%、三方里程两两 < 2%、加油对账 < 5%，同时通过才放行。 |
| **页面要素** | 三个并排"闸门"图标，每道闸门上方写自检名、下方写阈值与不通过动作：① **能量守恒自检**：瀑布图各分项之和 = 总能耗，**误差 < 3%**；② **三方里程自检**：车速积分 `s=∫v dt` / 里程表差分 `Δ(TotalVehicleDistance)` / GNSS 累积大圆距离，**两两偏差 < 2%**，以里程表为主、积分为高频细分、GNSS 做异常检测；③ **对账自检**：与加油/充电记录偏差 **< 5%**。底部一句话：三道全过才发布；任一不过 → 数据质量告警 / 信号核对 / 模型参数重标定。 |
| **口播要点（50 秒）** | 光有瀑布图不够，评委真正会问的是"**你凭什么说你算得准**"。我们的答案是三道自检，**三道全过才允许出报告**。第一道，能量守恒：瀑布图九个分项加起来必须回到总能耗，**误差小于 3%**。第二道，里程走**三条完全独立的路径**——车速积分、里程表差分、GNSS 大圆距离累积，两两偏差要小于 2%，偏差大了自动降级标注。第三道是硬碰硬：**跟加油小票对账，误差小于 5%**。这三道自检就是本方案和"跑个模型出个图"的区别——它让结论**敢拿去和车队对账**。 |

### 第 9 页 · AI 模型层：五个模型，AI 用在物理解决不了的地方

| 项 | 内容 |
|---|---|
| **标题** | 先物理，后 AI：AI 只学残差 |
| **核心信息（一句话）** | 基线预测给出"应该耗多少"，残差 = 实际 − 预测，才是 AI 的战场；再加异常检测、驾驶评分、CUSUM 衰减、LLM 报告。 |

## 三、评审高频提问与应答（18 组）

> **应答总原则**：先给结论 → 再给数字 → 最后给证据或动作。不回避、不吹大、"不知道"就说"这需要回去标定"。

### Q1. 这不就是常规的数据分析吗，AI 体现在哪里？

**A**：常规数据分析能算出"百公里 32 升"，但回答不了"**应该**是多少"。我们方案里 AI 有三个不可替代的位置，**而且这三层都已经在原型里真实跑出了数字**：

1. **基线预测（HistGradientBoostingRegressor / LightGBM）**——输入速度分布、驾驶激烈度 PKE、怠速、累计爬升、载荷、环境、工况结构等特征（原型实测 **80 车次 × 14 特征**，5 折交叉验证），预测"这台车这条线路这个载重**应该**耗多少"。原型**样本外 R² = 0.894、MAE = 1.71 L/100km、MAPE = 4.61%**。
2. **残差异常检测**——`r = 实际 − 预测`，残差 z-score 显著且为正，再用 IsolationForest 在"特征 + 物理残差"空间找离群点，**这一层不需要标签**。原型 80 车次上标记 **19 个可疑车次**，对应 **查准率 100%、查全率 79.2%、F1 0.884**，**56 个正常车次零误报**。
3. **可解释归因 + CUSUM 变点检测 + LLM 报告**——归因给的是**可溯源的证据条目**，例如某车次总残差 **+11.4%**、判定"**驾驶行为主导**"，证据是"行驶平均车速 59.0 km/h 高于同类（中位数 52.7 km/h），空气阻力能耗比同类高 26%"；CUSUM 盯残差均值持续上移，在故障码之前预警（原型实测 max=4.0，未触发阈值 12.0）。**查不出单一原因的车次判为「待人工判定」，不武断归咎于车辆**（见 Q17）。

**关键一句**：AI 用在**物理模型解决不了的残差**上，不是拿模型去硬拟合能耗总量。这也是我们样本需求低、结果可解释的原因。

### Q2. 没有真实数据，你怎么证明算得准？

**A**：我们分两层证明，**并且明确边界**。第一层不再是"目标值"，而是**已经跑出来的实测值**。

- **第一层（今天能证明的）**：原型里有基于纵向动力学生成的**带真值**的合成报文，含丢帧、突发丢包、噪声、时钟漂移、量化，可现场复现：

| 验证项 | 目标 | **原型实测** |
|---|---|---|
| 报文解码成功率 | ≥ 99.5% | **100.0000%**（235,711 帧 / 3 车次 / 11.8 MB） |
| 能耗 vs 仿真真值误差 | — | **0.01% ~ 0.05%** |
| 三方里程最大互差 | < 2% | **0.01% ~ 0.21%** |
| 燃油率积分 vs 累计油耗差分 对账误差 | < 5% | **1.08% ~ 3.57%** |
| 能量瀑布守恒自检残差 | < 3% | **~1e-14%（浮点零）** |
| 平均数据质量分 | — | **93.2 / 100**（A 级高置信） |
| 单车能耗分析耗时 | < 3 min | **约 0.04 s / 车次**（80 车次端到端约 70 s） |

  并且能检出人工注入的异常车次：80 车次中注入激烈驾驶 8、胎压不足 8、长时间怠速 4、燃烧恶化 4，**查准率 100%、查全率 79.2%、F1 0.884**（56 个正常车次零误报，19 个标记车次）。

- **第二层（拿到真车数据后的动作）**：仿真数据带真值，能先证明"算法算得准"；真车数据到手只换数据源，**模型与流水线不变**，然后跟**加油小票/充电订单**对账。

**我要主动说的边界**：仿真证明了**算法正确性**，不等于证明了**真车精度**。真车精度必须靠对账真值，所以我们阶段 0 的第一件事就是拿到加油小票和充电订单——**没有它就无法证明精度**，这句话我们写进了方案的待确认清单里。

### Q3. 你们怎么知道能耗高是车的问题还是司机的问题？

**A**：靠**同一个基线模型做控制变量**，再把残差归到人、车两条线上。**这里有一个如实说明**：80 样本下原型**没有**用第二个模型去做百分比责任分摊，而是**按证据类型判定**（下面第 3、4 条）；样本量上到几千条后再切回模型拆分。

1. **公平基线**：模型输入里已经包含线路地形、载重、车型车龄、温度、时段，也就是把"山区重载"和"城配空载"拉到同一条起跑线上，剩下来的残差才有可比性。
2. **拆分逻辑**：同一台车换司机 → 残差变了，指向**人**（急加速、怠速、经济车速偏离）；同一个司机换车 → 残差变了，指向**车**（喷油器、刹车拖滞、胎压、空滤、电机效率）。
3. **判决证据**：车的侧证据是物理项——无制动时仍有异常减速阻力、滚阻项持续高于同型车、同转速扭矩下降、`P_batt/P_wheel` 效率下降、同 SOC 区间压降变大；人的侧证据是行为项——急加速/急减速千公里次数显著高于同线路同车型司机、怠速时长占比突增。
4. **时间维度判决**：**CUSUM** 检测同车残差序列是否持续上移。司机行为通常短期波动大、长期均值稳定；车辆劣化是**持续单向漂移**——这条曲线能把两者分开。

一句话：**人的问题看行为特征，车的问题看物理残差，分不开的时候看 CUSUM 的时间趋势。**

**原型已经跑出了这张判定表**（80 车次，4 类故障人工注入，真值标签仅用于评测）：

| 注入故障 | 平均残差 | 未标记 | 待人工判定 | 车辆状况主导 | 驾驶行为主导 | 共同作用 |
|---|---:|---:|---:|---:|---:|---:|
| 燃烧恶化 `combustion_degraded` | +9.9% | 0 | 0 | **3** | 0 | 1 |
| 胎压不足 `tire_pressure_low` | +6.5% | 0 | 0 | **6** | 0 | 2 |
| 激烈驾驶 `aggressive_driving` | +2.6% | 5 | **1** | 0 | **2** | 0 |
| 长时间怠速 `excessive_idling` | −1.4% | 0 | 0 | 0 | **4** | 0 |
| 正常 `normal` | −2.3% | **56** | 0 | 0 | 0 | 0 |

**车辆类故障被判"车辆状况主导"、驾驶类故障被判"驾驶行为主导"** —— 这就是"是车的问题还是司机的问题"的机器答案。

**查不出来就说查不出来**：查不到单一物理原因的车次判定为**「待人工判定」**，说明"未定位到单一物理原因，建议人工复核数据质量与车辆技术状况"，**不武断归咎于车辆**（早期版本正是把这类车次直接判成"车辆状况主导"，会系统性冤枉车辆）。

> **要如实说明的一点**：80 样本下我们**没有**用第二个模型去做百分比责任分摊（曾试过"双基线"拆分，样本外 R² 反而从 0.742 掉到 0.700），改成了**按证据类型判定**——驾驶类证据 vs 车辆类证据。**宁可不给，也不给错**；样本量上到几千条后可以再切回模型拆分。（README 里写明的建议门槛是 **≥ 500 车次**。）

### Q4. 司机不配合怎么办？

**A**：这个问题我们当成**产品设计问题**，不是管理问题。四条具体做法：

1. **定位为辅助工具，不做考核**——方案里明确写"司机抵触被监控"的应对是"定位为辅助工具而非考核"。系统交付给车队长的是**改进建议**，不是罚单。
2. **公平基线是前提**——如果司机发现"我跑山区被拿去和城配比油耗"，这套系统第二天就死了。基线模型输入了线路地形和载重，**只和同类同线路的应该水平比**，这是司机愿意接受的前提。
3. **正向激励**——司机版报告叫《一对一驾驶改进建议》，措辞正向；同时输出**节油潜力榜/排行榜**，做奖励而不是处罚。
4. **脱敏**——司机姓名、工号与车辆数据**分离存储**，分析侧只用匿名 ID，展示层按权限回填。

**验证方式**：KPI 里"单车百公里能耗下降 3%~8%"的验证方式就是**整改前后同工况对比**——司机能看到自己的数字变好，配合度是收益驱动的。

### Q5. 节油 3%~8% 这个数怎么来的，是不是拍脑袋？

**A**：**不是我们拍的，但我们主动把它标成"需要标定"**。四点说明：

1. **来源**：3%~8% 参考的是**行业公开的车队能耗管理与驾驶行为改善经验区间**，方案第 8 节明确写了这个口径说明。
2. **我们自己不把它当结论**：原文写着"实际收益需以本车队基线数据标定"，并有 KPI 兜底——**指标"节油潜力测算偏差 < 30%"，验证方式是整改前后对比**。也就是说，我们连"测算准不准"都设了可验证的指标。
3. **对外只用保守值**：方案里写明"**报名/路演阶段建议先用保守值 3% 对外，避免夸大**"。所以今天我给你们的数字是 **100 台车年省 54 万起**，不是 144 万。
4. **量级不是空谈，原型给了实测数字**：
   - **能耗算法本身的精度**：报文反算能耗 vs 仿真真值误差 **0.01% ~ 0.05%**（单车 T000-2：燃油率积分 **8.804 L** vs 真值 **8.802 L**，误差 **0.03%**；体检报告主车次 T005-1：**12.635 L** vs **12.636 L**，误差 **0.00%**）——**这是能分辨 3% 量级变化的前提**。
   - **问题的能耗代价**：原型对四类典型问题做了人工注入并测出真实代价——胎压不足 **+9.5%**、激烈驾驶 **+7.8%**、燃烧恶化 **+10.0%**、长时间怠速 **+3.7%**。需要被找出来的问题本身就在 **3% ~ 10%** 量级，与"保守 3%"这个目标相称。
   - **同时如实说明**：单次行程的对账误差受 `TotalFuelUsed` 0.5 L 步进限制，量化下限本身就有 **4% ~ 6%**（T005-1 为 4.00%、T000-2 为 5.88%）。所以真车落地应按**加油周期长窗口**对账，而不是单次行程。

**收益的物理链条是清楚的**：单车年跑 80,000 km、30 L/100km、7.5 元/L → 年油费 **180,000 元**；3% 就是 5,400 元/车，100 台 **54.0 万**；5% 是 90.0 万；8% 是 144.0 万。这个算式谁都能验算，我们只是**不承诺区间上限**。

### Q6. 和市面上已有的车联网油耗分析产品有什么区别？

**A**：五点区别，都可以现场验证。

1. **可对账**——市面产品普遍给"百公里油耗"和报表，我们给**三道自检**：能量守恒 < 3%、三方里程两两 < 2%、**加油对账 < 5%**，不通过不出报告。原型实测：**守恒残差 ~1e-14%（浮点零）**、**三方里程最大互差 0.02%**（T005-1：车速积分 31.102 / 里程表 31.100 / GNSS 31.108 km）、**对账误差 1.08%**，三道全过。**结论敢和车队财务对账**，这是最硬的差别。
2. **可归因到分项**——别人给一个数，我们给**能量瀑布图**：怠速、附件、滚阻、风阻、坡道、净加速、制动耗散、传动损失逐项拆开，各项之和回到总量（原型 T005-1：怠速与附件 0.84、传动损失 3.24、热效率损失 84.83、车轮牵引 37.28，合计 **126.19 kWh**，与实测 **126.19 kWh** 一致）。
3. **公平比较**——我们有**基线预测模型**做公平比较器，解决"山区重载 vs 城配空载不能直接比"这个行业老问题（原型样本外 **R² = 0.894**、**MAPE = 4.61%**）；市面产品多数还是同型车均值对比。
4. **AI 用在残差上 + 结论可溯源**——异常不是报警阈值，而是残差 + IsolationForest 离群 + 物理规则三路证据合并，**每条结论可溯源到具体证据条目**（原型实测 **查准率 100%、查全率 79.2%、F1 0.884**，56 个正常车次零误报）。
5. **分不清就明说**——胎压不足与燃烧恶化**仅凭油耗不可辨识**（见 Q17），所以我们先给候选假设、再用**独立观测量（胎压信号）**判别；查不出单一原因就判**「待人工判定」**，不硬给结论。这一条市面产品几乎没有。

**另外两点落地差异**：架构与车型解耦，**只换 DBC 和参数集**就能换车型；**不依赖新硬件**，复用现有 T-Box。

### Q7. 样本量不够怎么训练模型？

**A**：我们的架构天生对样本量不敏感，有三道缓冲。

1. **物理模型兜底**——能耗的主体由能量守恒算出来，AI 只学残差。**没有模型，能耗账本和瀑布图照样出**，只是少了"应该多少"的对比。这意味着**冷启动不会失败**。
2. **分层聚合**——基线按车型+线路分层，样本不足时先用**同型车/同线路聚合**训练（方案阶段 2 明确写了这一条），再把单车残差算出来。
3. **无监督路线**——异常检测里 IsolationForest **不需要标签**；CUSUM 是单序列变点检测，一台车的历史就能用。

**样本门槛**：阶段 0 只要 **≥3 台车 ≥5 天**的原始报文就能跑通 MVP。而且数据是持续产生的——车队每天新增的数据会自然地把模型喂起来，这是"持续积累数据后迭代"的路径。

**原型就是小样本的实证**（**80 车次 × 14 特征**，HistGradientBoosting + 5 折交叉验证）：

- 样本外 **R² = 0.894**、**MAE = 1.71 L/100km**、**MAPE = 4.61%** —— 80 个样本就能把基线做到这个水平，因为**特征里已经含了物理量**（载荷、坡度、车速带占比），模型只需要学残差结构。
- 前 5 重要特征：`payload_t`(6.88)、`grade_up_m`(1.17)、`grade_down_m`(0.70)、`speed_band_0_10_pct`(0.34)、`distance_km`(0.32) —— 排第一的是**载荷**，符合物理直觉，说明模型学到的不是噪声。
- **哪些事 80 样本做不了，我们如实说**：曾试过用"双基线"模型（含/不含驾驶特征）去**按百分比拆分责任**，样本外 R² 反而从 **0.742 掉到 0.700**，拆分结果是噪声，所以最终改成**按证据类型判定责任**；异常检出**查全率 79.2%**（漏报 5 个车次，全部是激烈驾驶——注入的超速被功率可达性约束部分抵消，实际车速差异只有约 +6%，低于判据阈值），真实场景要靠维修工单做闭环回流降低漏报。README 里写明了：**建议 ≥ 500 车次再启用模型化的责任拆分**。

### Q8. 数据涉密 / 涉个人信息怎么处理？

**A**：方案第 3.4 节有明确的三条，我按数据流说：

1. **个人信息与车辆数据分离存储**——司机姓名、工号与车辆数据**分离**，分析侧只用匿名 ID，展示层按权限回填。也就是**算法侧看不到人**。
2. **分层存储 + 脱敏训练**——原始报文按"**热 30 天 + 冷归档 1 年**"分层存储，**脱敏后**才可用于模型训练。
3. **输出侧收敛**——对外汇报**只出聚合结论**，不出现可定位到个人的轨迹细节。

**待确认的合规边界**：司机个人信息的脱敏与使用边界**由谁审批**，我们列在"待确认信息"清单第 7 条里，需要业务方和法务一起定。**我们不自作主张**。

### Q11. LLM 会不会编数字？

**A**：**架构上就不允许它编**，有四道锁：

1. **职责锁**——大模型只做"**翻译与表达**"，所有数字由物理模型和统计模型计算，这是方案里写死的约束。
2. **输入锁**——喂给 LLM 的是**固定 JSON Schema** 的结构化结果（能耗瀑布、残差、异常项、SHAP Top-5、对账结果），**它看到的就是算好的数字**，没有让它推算的输入。
3. **Prompt 锁**——Prompt 里硬约束"禁止生成或推算数值"。
4. **输出锁**——报告发布前做**数值回校验**：正则提取报告里的数字，**与源数据比对，不匹配则拒绝发布**。

**兜底**：即使 LLM 接口不可用，原型里报告模块可以输出 Markdown 体检报告和能耗瀑布图（`src/report.py`），**流水线不依赖大模型也能出结论**。这一点在现场演示的兜底方案里也有对应安排。

### Q12. 项目失败的最大风险是什么？

**A**：**最大风险不是算法，是数据拿不到。** 方案风险表里"拿不到真实报文数据（保密/流程慢）"可能性中、影响高，我们有三步对策：

1. **提前走数据申请流程**——把它放在阶段 0 的第 1 天，而不是等到建模时才发现没数据。
2. **仿真数据先跑通全链路**——原型已完成，仿真数据**带真值**，可以先证明"算法算得准"；拿到真车数据后**只替换数据源，模型与流水线不变**。
3. **脱敏后的单台车样本做 PoC**——最小化客户的合规顾虑。

**如果一定要排第二风险**，是"**对账误差打不进 5%**"。对策是**两条路径对账交叉**——燃油率积分（`EngineFuelRate` 实时积分）与累计油耗差分（`TotalFuelUsed` 总油耗计数器）——再叠加**三方里程校验**（车速积分 / 里程表 / GNSS）；偏差大时**自动定位是哪个信号的问题**；必要时用**长窗口对账**（因为 `TotalFuelUsed` 步进 0.5 L，短行程天然对不准）。原型三种演示车次的实测对账误差是 **1.08% / 1.10% / 3.57%**，都在 5% 以内；其中 3.57% 那一趟的量化下限本身就是 5.88%，说明**这个风险主要来自数据分辨率，而不是算法**。

**还有一个不要脸的诚实答案**：如果对账真打不进 5%，那就说明数据质量不支持结论，我们会**降级标注置信度、不输出误导结论**——这本身就是方案里的设计。

### Q13. 为什么先做仿真，是不是没有真实数据？

**A**：**这是主动的工程选择，不是被动妥协**，三个理由：

1. **真值问题**——真实数据**没有真值**。你拿真车数据算出"百公里 32 升"，怎么知道是 32 还是 30？仿真数据基于纵向动力学生成，**每一项能耗的真值都是已知的**，才能验证"算法算得准"。
2. **异常可控**——我们可以**人工注入**高怠速、急加速、滚阻恶化的异常车次，验证检出能力。原型 80 车次里注入了四类故障（激烈驾驶 8、胎压不足 8、长时间怠速 4、燃烧恶化 4，其余 56 个正常），实测 **查准率 100%、查全率 79.2%、F1 0.884**，其中胎压不足 **+9.5%**、激烈驾驶 **+7.8%**、燃烧恶化 **+10.0%**、长时间怠速 **+3.7%** 都是真实测出来的能耗代价。真实数据里等一个喷油器衰减，可能要等几个月。
3. **脏数据可复现**——丢帧、突发丢包（2.5~8 秒）、噪声、时钟漂移、量化误差都能按需注入，把第 6 页讲的数据质量问题**变成可回归测试的用例**（原型实测平均质量分 **93.2**、最长信号空档 6.4~8.0 秒全部被插值补全，说明补全逻辑是真的在被测试）。

**边界照旧**：仿真证明算法正确性，真车精度靠加油小票对账。**我们从来没有用仿真数字去替代真车精度这个指标。**

### Q14. 车联网平台已经有了，为什么还要你们这一层？

**A**：因为现有平台停在**"监控与回放"**，我们做的是**"归因与对账"**。

| 维度 | 现有车联网平台 | 本方案 |
|---|---|---|
| 数据用途 | 实时监控大屏、故障回放 | 能耗账本、分项归因、节油建议 |
| 输出 | 油耗曲线、报表 | **能量瀑布图**（9 个分项） |
| 精度 | 通常无对账机制 | **三道自检**：守恒 < 3%、里程 < 2%、对账 < 5%（原型实测 **~1e-14% / 0.02% / 1.08%**） |
| 比较 | 同型车均值 | **AI 基线模型**，公平比较器（原型样本外 **R² = 0.894**、**MAPE = 4.61%**） |
| 异常 | 阈值报警、故障码 | 残差 + IsolationForest + 物理规则三路证据 + **CUSUM 提前预警** + **查不出就说「待人工判定」**（原型实测 **查准 100%、查全 79.2%、F1 0.884**，56 个正常车次零误报） |
| 报告 | 图表 | 三种读者的**中文诊断报告 + LLM** |

**关系定位**：我们不替换平台，**我们吃平台已有的数据**。复用现有 T-Box，增量硬件成本为零——这也是评委最容易接受的落地方式。

### Q15. 这套方案除了商用车，还能用到哪？

**A**：**架构与车型解耦，换 DBC 和参数集就能换对象**，这是方案里明确写的可复制性。

- **横向（同行业不同动力）**：燃油 / 纯电 / 混动都已经在方案里覆盖——燃油走 `EngineFuelRate` 积分加 `TotalFuelUsed` 对账；纯电走 `P_batt = U·I` 加 ΔSOC 校验，并且单独拆出空调加热附件（**冬季电车附件可占 20%~35%**）。
- **纵向（同技术不同对象）**：任何有 CAN 数据的设备都能用同一套方法——工程机械、叉车、港口设备、公交、冷链车。**核心不变的是"物理守恒 + 残差 AI + 三道自检"这套方法论。**
- **规模化路径**：单车用 pandas 足够快，车队上 PySpark；存储从对象存储 + 时序库 + 列存分析库起步，需要时再接调度系统做车型-线路匹配优化。

**一句话收**：我们交付的不是一个油耗报表，是一套**"从报文到可对账结论"的方法论**，换一个 DBC 就能重新落地一次。

### Q16. 仿真数据能说明什么？不能说明什么？

**A**：这张表我们贴在自己工位上，**防止把仿真结论说过头**。一句话结论：**仿真能证明"算法自洽且算得准"，不能替代真车验证。**

| 维度 | 仿真数据**能**说明 | 仿真数据**不能**说明 |
|---|---|---|
| 算法自洽性 | 报文逐位编码 → 解码 → 清洗 → 能耗反算全链路跑通，**235,711 帧解码成功率 100.0000%** | 真实 DBC 缺失/保密、信号命名不一致、厂商私有 PGN 的兼容性 |
| 物理正确性 | 能量瀑布守恒残差 **~1e-14%（浮点零）**；三方里程最大互差 **0.01% ~ 0.21%** | 真车传感器标定偏差、里程表脉冲系数误差、安装角度误差 |
| 数值精度 | 能耗 vs 真值误差 **0.01% ~ 0.05%**；对账误差 **1.08% ~ 3.57%** | **真车精度**——仿真真值是我们自己生成的，等于"用出题人的答案阅卷" |
| 异常检出能力 | 有故障真值标签时 **查准率 100%、查全率 79.2%、F1 0.884**，56 个正常车次零误报 | 真实车队的故障分布、复合故障、未建模的故障类型；**真实车队没有故障标签，查准/查全本身是仿真专有指标** |
| 故障可辨识性 | 能**暴露算法边界**：实测"滚动阻力能耗"恒为常数（`crr_est` 恒 0.02040），**不能**当滚阻检测器；胎压不足与燃烧恶化的能效反标定值 **0.3122 vs 0.3125**，**仅凭油耗不可辨识**（见 Q17） | 真实数据上这两条边界的具体数值是否相同（但结论方向一致：必须靠独立观测量或滑行试验） |
| 归因逻辑 | 车况类故障判"车辆状况主导"、驾驶类故障判"驾驶行为主导"，查不出单一原因判**「待人工判定」**，可用人工真值核对 | 真实维修工单能否对上、误报在真实使用场景里的代价 |
| 工程性能 | 235,711 帧解码**约 8.5 s**、单车能耗分析**约 0.04 s**、端到端**约 70 s** | 车队级数据量（GB/天）与生产环境下的时延、并发与存储成本 |

**所以我们的对外口径是**：拿到真车数据后，**第 3.1 节的精度指标必须用真值重新实测一遍**，不能直接沿用仿真结论（这条写在 `prototype/README.md` 第 6 节）；仿真数据的作用是**在真车数据到位之前，把算法、流水线、判据门限全部调到可用状态**，让真车数据一到就能跑对账，而不是从零开始。

### Q17. 你怎么区分"车的问题"和"司机的问题"？如果都查不出来呢？

**A**：分四步，最后一步是**承认查不出来**——这不是话术，是原型实测逼出来的结论。

1. **先做公平比较**：基线模型输入线路、载重、车型车龄、温度、时段，先算出"应该耗多少"，残差才有可比性（模型本身不含驾驶行为特征，所以残差 = 驾驶行为 + 车辆状况 + 其他超额消耗）。
2. **再按证据类型归因**：行为类证据（急加速/急减速、怠速、经济车速偏离、平均车速与风阻）→ **驾驶行为主导**；物理类证据（无制动时仍有异常减速阻力、整体能效反标定偏低、胎压信号偏低）→ **车辆状况主导**；两类都有 → **共同作用**。
3. **但有一个必须正视的可辨识性边界（原型实测结论）**：
   - 分析侧永远按**铭牌滚动阻力系数**计算，所以"滚动阻力能耗"在所有车次上是**常数**（实测 `crr_est` 恒为 **0.02040**）——**它作为滚阻故障检测器完全无效**。初版把它当判据，等于埋了一条永远不会触发的规则。
   - "胎压不足"与"燃烧恶化"的**整体能效反标定值几乎完全相同**（实测中位数 **0.3122 vs 0.3125**）——**仅凭油耗数据二者本质不可辨识**，因为"阻力变大"和"效率变低"表现为同样的油耗上升。

   → 所以方案的处理方式是：**先给两个候选假设，再用独立观测量判别**。有胎压信号就用胎压信号（原型为此在 DBC 里增加了 `TRK_TPMS1` 报文，现在是 **11 条报文 / 25 个信号**）；没有胎压信号的车型，必须做**滑行试验（coast-down）反标定滚阻**，否则只能说"能耗偏高、原因待查"。

   **T005-1 就是这条路径的真实实证**（体检报告第八节原文）：

   > 相对作业基线 **+11.1%**（z=+2.06，严重度 中，判据：物理规则/统计残差）→ 判定：**车辆状况主导**
   > 【车辆状况】**胎压 607 kPa 显著低于标准 822 kPa**，滚动阻力将升高，建议补气并复测能耗

4. **如果两条路都查不出来**：判**「待人工判定」**，报告里明说"能耗显著高于同类应达水平，但未定位到单一物理原因，建议人工复核数据质量与车辆技术状况"。80 车次评测里就有 1 个激烈驾驶车次落到这一档（`T000-1`，残差 +3.6%，仅有无监督离群证据）。**我们宁可给"待人工判定"，也不硬扣一顶帽子。**

> **一句话**：能分的分（车况 / 驾驶）；分不清的用**独立观测量**分（胎压信号、滑行试验）；实在分不清的**明说分不清**——**宁可不给，也不给错**。

### Q18. 你说能耗误差只有 0.05%，那车轮侧分解误差 9% 是不是算错了？

**A**：**没有算错，但这里必须把"账算得准"和"分解算得准"分开说** —— 这是两个不同层级的量，混在一起讲就会自相矛盾。

| 层级 | 精度 | 说明 |
|---|---|---|
| **能耗账目**（燃油升数 / 化学能总量） | **0.01% ~ 0.05%**（T005-1：燃油 12.635 L vs 真值 12.636 L，**0.00%**） | 由 `EngineFuelRate` 积分 + 能量守恒得到，**这才是"可对账的那个数"**，也是 0.05% 的所指 |
| **车轮侧物理分解**（滚阻 / 风阻 / 坡道各占多少） | 按**铭牌参数**计算。正常车次分项误差很小；**滚阻实际恶化 35% 的车次上，分项差 9% ~ 17%**（T005-1：`e_traction_wheel_kwh` 差 **9.08%**、`e_brake_req_kwh` 差 **16.73%**） | 分解用的是**铭牌 C_rr**；车一旦出问题，铭牌参数就不再代表这台车 |

**为什么说这不是缺陷，反而正是 AI 要检测的信号本身**：

1. **分解的职责不是"永远对"，而是"当基准"**——只有假设车辆健康，物理分解才能当一把标准尺子。这是个**前提假设**，不是精度承诺。
2. **分解对不上，本身就是"车辆参数变了"的证据**——这趟车滚阻实际大了 35%，分解必然偏，而**偏差的方向和量级恰好指向"滚阻异常"这个故障假设**；这正是 Q17 里 `eta_engine_est` 反标定与胎压规则要抓的东西。
3. **账目在故障车上依然准**：T005-1 是**故障车**，它的三道自检**依然全部通过**——守恒残差 **1.13e-14%**、三方里程互差 **0.02%**、对账误差 **1.08%**。也就是说"**这趟车油耗算得准**"和"**这趟车滚阻异常**"可以同时成立，而且我们两个都报。
4. **这也正是方案不满足于"给一个油耗数字"的原因**：账目准，只能回答"烧了多少"；**分解偏，才能回答"烧在哪、哪里坏了"**。

> **一句话**：**账要准（0.01% ~ 0.05%），分解要诚实（差多少就报多少）**。分解与真值的偏差不是精度事故，而是**故障检测的输入信号**。

## 五、答辩 3 分钟极简版口播稿（逐字稿，被打断也能快速讲完）

> **节奏**：约 780 字，正常语速 3 分钟。**加粗处为重音，必须咬清数字。**

---

**【0:00–0:30 问题】**

各位评委好，我们是 XX 队。我先说一个问题。

车队里每台车每天都在产生**GB 级的整车 CAN 报文**，采样率 10 到 100 赫兹，里面的信号非常全——发动机转速、喷油率、扭矩、车速、挡位、电池电压电流，什么都有。但这些数据的用途，今天基本只有两个：**大屏监控**和**故障回放**。

而车队长每天问的问题是——**"这台车今天为什么多烧了 8 升油？"**

一边是满屏十六进制，一边是一句业务问题，中间那层翻译，今天靠人肉，**一台车一天要 4 小时以上**。

**【0:30–1:10 方案】**

我们做的事情，就是把这段数据翻译成三样东西：**可对账的能耗账本、可解释的能耗拆解、可执行的节油建议**。

技术路线一句话：**先物理，后 AI**。

先用能量守恒把能耗拆成九个分项——怠速、附件、滚动阻力、空气阻力、坡道、加速动能、制动耗散、传动损失，画成一张**能量瀑布图**；然后让机器学习去学物理模型解释不掉的**残差**——残差显著为正，就说明这台车这段行程比同类应该的水平更耗能，进入归因。

AI 用在四个地方：**基线预测**给出"应该耗多少"，原型实测样本外 **R² = 0.894、MAPE = 4.61%**；**残差异常检测**识别九类问题，从喷油器衰减到胎压不足，原型实测 **查准率 100%、查全率 79.2%、F1 = 0.884**，56 个正常车次**零误报**；**归因判定**把"这台车比基线高 11.1%"变成"**车辆状况主导**，证据是胎压 607 千帕显著低于标准 822 千帕"；**CUSUM 变点检测**把故障发现提前到故障码之前。最后大模型只做一件事——**把数字翻译成中文报告，所有数字都由物理和统计模型算出，禁止它编。**

**这里我要主动补一句边界**：我们从油耗数据里发现，**"胎压不足"和"燃烧恶化"本质不可辨识**——两者的整体能效反标定值几乎相同（实测 0.3122 vs 0.3125）。所以方案不硬猜：**先给两个候选假设，再用独立观测量判别**（胎压信号，或没有胎压信号时做滑行试验）；实在分不清的，判**「待人工判定」**，**宁可不给，也不给错。**

**【1:10–1:50 凭什么准】**

评委一定会问，你凭什么说你算得准。我们的答案是**三道自检，三道全过才发报告**——这三道在原型上已经真实跑过：

第一，**能量守恒**——瀑布图九个分项加起来必须回到总能耗，误差小于 **3%**，实测 **1.13e-14%（浮点零）**。
第二，**三方里程**——车速积分、里程表、GNSS 三条独立路径，两两偏差小于 **2%**，实测 **0.02%**。
第三，**加油对账**——跟加油小票比，误差小于 **5%**，现场演示跑到的是 **1.08%**（三条演示车次 1.08% ~ 3.57%）；同时跟仿真真值只差 **0.00%**。**这里要补一个限定语：这个 0.05% 以内指的是"能耗账目"的误差**——燃油升数、化学能总量；**车轮侧的分项分解是按铭牌参数算的，故障车次上会差 9% 以上，而那恰恰是 AI 要抓的信号。**

这三道自检，就是这个方案和"跑个模型出个图"的区别——**它让结论敢拿去和车队财务对账。**

**【1:50–2:35 价值】**

价值两个数字。

**效率**：单车单日分析，人工 **4 小时**以上，自动化 **3 分钟以内**（原型实测 80 个车次端到端**约 70 秒**、单车能耗分析约 0.04 秒），**提效超过 80 倍**；100 台车的周报，人工 3 人天每周，自动化是 0，一年省下大约 **150 个人天**。

**收益**：一台车一年跑 8 万公里，百公里 30 升，油价 7.5 元，**一台车一年油费 18 万**。100 台车，按**最保守的 3% 节能率**，一年省 **54 万**；到 8% 是 **144 万**。而且**不依赖任何新硬件**，用的就是车队现有的 T-Box。新能源车同样适用，100 台电车按 5% 算一年省 **38.4 万**。

**【2:35–3:00 落地与收口】**

落地路径也很具体：**不新增硬件，MVP 5 天就能跑通真车数据，全链路 13 天到可演示状态**。从报名截止 9 月 30 到路演 10 月 13，13 天倒排，每个阶段的交付物在方案里都写清楚了。

最后用一句话收口：我们做的事情，是把**满屏十六进制**，变成**一句司机明天就能执行的话**——"你这趟车的**滚动阻力耗能 14.7 度电，占整车能耗 11.7%**，判定为「车辆状况主导」——**胎压 607 千帕，低于标准 822 千帕**；**补气后复测**，下一趟就能看到数字变化"。
