### 2.1 RLS 质量辨识：文档声称已实现，代码中不存在

**文档声称**

- `方案文档/01` §4.4.4 / §9 / §10：质量未知→「无传感器时用**递推最小二乘（RLS）质量辨识**」
- `方案文档/02` 演讲词：「我实现了……质量与坡度的估计（**RLS 质量辨识**、卡尔曼坡度融合）」

**代码实际**（`src/preprocess.py:339`）

```python
def estimate_mass(frame: SignalFrame) -> tuple[np.ndarray, str]:
    """整车质量估计：优先轴荷/悬架信号，缺失时回退油耗-动力学一致性辨识。"""
    if frame.has("TotalVehicleMass"):
        m = frame["TotalVehicleMass"]
        return moving_average(m, int(20 * GRID_HZ)), "轴荷/悬架传感器"
    return None, "不可用"          # ← 文档所述的 RLS 回退路径并不存在
```

全仓库检索 `RLS|递归最小二乘|recursive_least`：**仅命中 `.md` 文档，`.py` 代码零命中**。

**影响**：无轴荷信号时，`energy.analyze_frame` 会静默回退到**铭牌质量** `params.mass_kg()`（`energy.py:214`），而不是辨识质量。这是"静默降级"——不报错、不标记，直接给出失真结论。对重载变化的真实车队，这会系统性污染整条瀑布分解与残差。

**建议（二选一）**：① 补实现（约 40 行：加速段 `m̂=(F_drive−F_resist)/a` 递推 + 工况筛选）；② 或**如实改写文档**为"轴荷传感器方案 + 后续扩展"，并把该回退标注为"未实现，当前以铭牌质量兜底且质量分降级"。

roll_kwh_per_km / mass_t : min=0.02042  max=0.02043  相对离散=0.003%

### 2.5 【真实缺陷】"所有车次峰值发动机需求 ≤ 347 kW"不成立，且根因是仿真器自身的物理约束失效

**文档声称**（`prototype/README.md` §5.2）：

超限明细（前 6 名）：

| 车次 | 注入故障 | 发动机峰值 kW | 车轮峰值 kW |

    ...

而真值能耗计算时却施加了故障倍数：

```python
p = ph.road_load_power(v, a, grade, params, c_rr_scale=spec.c_rr_scale)  # ← 这里才有
```

于是**胎压不足的车次（`c_rr_scale=1.35`）**在求解时按正常滚阻放行、在实际算能量时却被要求多输出 35% 的滚阻功率 —— 功率自然冲破上限。这解释了为什么超标最严重的 6 个车次**全部是 `tire_pressure_low`**。

- 对**能耗账目**无影响（账目精度仍 0.01%~0.05%）；
- 对**"真值物理自洽"这一宣称有实质影响** —— README §5.2 整节在讲"初版仿真器有若干看起来对其实不可能的问题，已全部修正"，而这一类问题**并未修正干净**；

## 3. 🟠 中等：评测方法与口径

### 3.1 "三道自检"中有两道是代数恒等式，不是验证

README §3.1 把"能量守恒自检残差 ~1e-14%"列为精度指标，方案文档 01 第 5 项同样如此。**实验 A** 直接检验了它的鉴别力：故意用**严重错标**的整车参数重算同一份报文日志——

| 参数设定 | 守恒残差% | 车轮恒等式% | 里程互差% | 对账误差% | 三道自检 | 牵引能耗 kWh |
|---|---:|---:|---:|---:|---|---:|
| 基准（铭牌参数） | 0.00e+00 | 2.64e-14 | 0.03 | 3.57 | 全部通过 | 26.87 |
| 风阻系数 C_d ×1.6 | 0.00e+00 | 0.00e+00 | 0.03 | 3.57 | **全部通过** | 31.23 |
| 迎风面积 A ×1.5 | 0.00e+00 | 1.17e-14 | 0.03 | 3.57 | **全部通过** | 30.47 |
| 滚阻系数 C_rr ×3.0 | 0.00e+00 | 1.69e-14 | 0.03 | 3.57 | **全部通过** | **42.06** |
| 整备质量 +8000 kg | 0.00e+00 | 2.64e-14 | 0.03 | 3.57 | **全部通过** | 26.87 |

牵引能耗从 26.87 kWh 变成 42.06 kWh（**偏差 57%**），三道自检**全部绿灯**。

原因是代数上的：

- **守恒自检**：`thermal = 总能量 − 怠速 − e_trac_engine`（`energy.py:191`）——最后一项是**配平项**，因此残差恒为 0。代码注释其实已经诚实写明「瀑布**按定义闭合**，此处记录数值以便审计」，且 `passed=True` 是**硬编码**的。
- **车轮恒等式**：`e_trac − (Σwheel + e_brake) ≡ 0`，因为 `p_traction = clip(p_total,0,·)`、`p_brake = clip(−p_total,0,·)` 与 `wheel` 四项共享同一个 `p_total`。
- **里程互差 / 对账误差**：只依赖报文信号（车速、里程表、GNSS、燃油率、累计油耗），**与整车参数无关**，因此不可能发现参数错标。

**结论**：三道自检实际只能验证"**报文链路与账目自洽**"，**不能验证"物理模型算得对"**。目前文档把它呈现为后者。

**建议**：
1. 把"能量守恒残差 ~1e-14%"从**精度指标表**中移出，改列入"账目自洽性"说明，并明确标注其为恒等式；
2. 真正的物理验证应使用**独立观测量**：例如拿真车的**滑行试验（coast-down）**反标 `C_rr`、用**称重**校核质量、用**实测风洞或长巡航段**反标 `C_d·A`，再看瀑布各分项是否收敛；
3. 增加一个"**参数扰动敏感性**"小节——主动展示"参数错标 X% 会导致哪个分项偏 Y%"，这比一条恒等于零的残差更有说服力，也更能体现团队真的理解模型边界。

### 3.2 `decode_success_rate` 只统计 CAN ID 命中，与"信号完整性"无关

**实验 J** 用三种方式破坏日志后重测"解码成功率"：

```
原始日志 79,133 帧（同一份 DBC 编码而来）
(a) 原样解码                     成功率 100.0000%   失败 0
(b) 破坏 5% 帧的尾字节后          成功率 100.0000%   失败 0     ← 破坏无感
(c) 注入 500 帧未知 CAN ID 后     成功率  99.3682%   未知ID 500  ← 只有这条会掉
```

**破坏 5% 帧的载荷字节，成功率纹丝不动**——因为 DBC 未定义 CRC/校验，`cantools.decode_message` 对任意 8 字节载荷都能"成功"解出一组数值。

**结论**："报文解码成功率 100.0000%" 的准确名称是「**CAN ID 在 DBC 中的命中率**」，它**不度量**信号完整性、不度量解析鲁棒性。更值得注意的是它隐含的风险：**被破坏的帧会被静默接受为有效数据**。

值得肯定的是，作者在 `preprocess.score_quality` 中做了量程断言（`RANGE_CHECK`）与卡死检测，这才是真正兜住损坏数据的机制——但它藏在质量分里，没有被当作对应指标陈述。

**建议**：
1. 把该指标更名为「ID 命中率」；
2. 补充一个**真正的解析鲁棒性实验**（如实验 J 的 (b) 用例）：注入位翻转/截断帧，验证质量评分能否识别并降级——这既诚实，又能把 `score_quality` 这块真正的工作量展示出来；
3. 生产环境接入真车 DBC 时，**务必**确认是否有 CRC 校验字段。

### 3.3 异常判据的阈值取材于被评测的同一批数据

`detect_faults` 的规则阈值由**传入特征表自身**算出（`rule_threshold` 取 `P90` / 中位数倍数），统计判据的 z 也取自同一批数据。因此"查准率 100%、查全率 79.2%"是**全量自评**结果。

**实验 D2** 做了折半交叉验证（阈值只在 A 半标定，在 B 半评估，5 次随机折半）：

| 方式 | 查准率 | 查全率 |
|---|---|---|
| 全量自评（文档口径） | 100.0% | 79.2% |
| 折半交叉验证（5 次均值） | **100.0%** | **70.8%** |

**结论（一半是好消息）**：
- **查准率 100% 是稳健的** —— 在阈值外推的情况下**零误报**依然成立。考虑到"56 个正常车次零误报"是文档反复强调的卖点，这个结论**经受住了检验**，值得在路演中更有底气地讲。
- **查全率存在约 8.4 个百分点的乐观偏差**（79.2% → 70.8%），文档应如实标注为"全量自评口径"。

### 3.4 车队工况高度同质，R² 主要来自载荷

**实验 N**（特征子集对照）：

| 特征集 | 特征数 | 样本外 R² | MAPE |
|---|---:|---:|---:|
| 仅 `payload_t`（整车总质量） | 1 | **0.797** | 6.37% |
| 仅 `distance_km` | 1 | −0.091 | 14.79% |
| 载荷 + 地形（4 项） | 4 | **0.909** | 4.35% |
| 载荷+地形+环境（7 项） | 7 | 0.907 | 4.37% |
| **完整作业基线（文档口径）** | **14** | **0.894** | **4.61%** |

**实验 N2**（工况多样性）：

| 量 | 范围 | 相对离散 |
|---|---|---:|
| `avg_speed_moving_kph` | 49.3 ~ 60.0 km/h | **2.9%** |
| `distance_km` | 28.9 ~ 34.7 km | **2.4%** |
| `payload_t` | 14.5 ~ 34.4 t | **23.9%** |
| 目标油耗 | 25.3 ~ 50.8 L/100km | 17.3% |

**两个结论**：

1. **单个特征（整车总质量）就拿到了 0.797 的 R²**，占 14 特征模型 0.894 的绝大部分。原因很清楚：仿真器里**所有 80 个车次共用同一套 30 分钟工况骨架**（起步怠速 → 4×城市启停 → 城郊 50 → 高速 80 → 市区 35），差异只来自 `style(0.85~1.2)`、`speed_scale(1.0/1.12)`、`payload(5~25t)`、`route_seed(0~5)`。车队里真正有方差的只有**载荷和地形**。真实车队的城市配送 vs 干线长途工况差异远大于此。
2. **4 个特征（载荷+地形）的 R²=0.909 反而高于文档口径的 14 特征 0.894** —— 也就是说 6 个 `speed_band_*` 特征 + `distance_km`/`ambient_c`/`cruise_time_pct` 给模型**净增加了噪声**。

**建议**：
- 在 §7「已知局限」中**明确加入"仿真车队的工况同质性"**这一条，并说明因此 R²/MAPE 相对真实车队是**乐观**的；
- 考虑把作业基线精简为载荷+地形核心特征（更少特征、更高 R²、更好解释），或至少说明为何保留 14 个；
- 若时间允许，**给仿真器加入 2~3 种差异化的工况骨架**（城市配送短驳 / 城际中速 / 干线高速长途），这会显著提升原型的说服力——因为"公平比较器（山区重载不与城配空载比）"正是方案的核心卖点，而当前数据里几乎没有"城配 vs 干线"这种维度。

### 3.5 `peer_residual` 的"同类"里混着同类型故障车

**实验 F**：对每个车次取 9 个近邻（按 `payload_t`/`distance_km`/`grade_abs_mean` 标准化距离），统计近邻中故障车占比：

```
每个车次的 9 个近邻中，故障样本占比：均值 22.2%，最大 56%
（车队整体故障比例 30.0%）
```

近邻基线把"同类型故障车"也算作正常参照，会**抬高基准、压低偏差**。实测 `tire_pressure_low` 的同类偏差只有 +2.55%，而其模型残差是 +6.48%——**近邻法对该类故障的灵敏度显著弱于模型基线**。

**建议**：在计算近邻中位数时**剔除已被标记为异常的车次**（迭代一次即可），或在文档中说明该保守性。

### 3.6 检测能力主要来自物理规则，残差统计判据贡献很小

**实验 N3**：单独使用"残差 z ≥ 1.8 且残差 > 1.5%"这一纯统计判据：

```
命中 3 例：故障 3 例，正常 0 例
明细：{aggressive_driving: 1, combustion_degraded: 1, tire_pressure_low: 1}
查准率 100.0%   查全率 12.5%
```

全系统最终标记 19 个可疑车次，其中纯统计路径只贡献 **3 个**。其余检出几乎全部来自物理规则（怠速、`eta_engine_est`、车速/风阻）。

**结论**：这不是缺陷（README §5.4 明确写了"物理规则最可解释、小样本最稳健"），但对外表述"**三级判据**"容易让人以为 AI 模型承担了主要检出工作，**实际承担主力的是物理规则**。"AI 学物理模型解释不掉的残差"这一叙事在**归因/责任判定**上成立，在**检出**上贡献有限。建议如实表述。

### 3.7 `permutation_importance` 用训练集预测自证

`ai_models.permutation_importance` 用 `model.predict(X)`，而 `model` 是在**同一份 X, y** 上 `fit` 的（`ai_models.py:83` 与 `:98`）。样本外残差做得很规范（`cross_val_predict`），但特征重要度回落到了**训练集自证**。在 80 样本、`max_depth=4`、`max_iter=400` 的配置下这会让重要度被高估。`n_repeat=3` 也偏低（建议 ≥ 10）。

**建议**：改用折外预测计算重要度，或直接说明其为"训练集置换重要度"。

### 3.8 特征分组与自身设计原则的两处不一致（实测影响小，但逻辑上该修）

README §5.3 明确指出「`avg_speed_kph` / `duration_s` / `idle_time_pct` 必须排除」，且 `DRIVING_FEATURES` 已包含 `avg_speed_moving_kph`、`max_speed_kph`。但：

| 项 | 问题 | 实测影响 |
|---|---|---|
| `speed_band_*_pct` × 6 | 车速**分布**（按行驶时间归一）与 `avg_speed_moving_kph` 信息高度重叠，却**留在了作业基线内**，与"车速选择属于驾驶员决策，必须排除"的原则矛盾 | **实验 C**：剔除后激烈驾驶平均残差 +2.67% → +2.55%（仅 0.12 pp），且 R² **上升** 0.894→0.916。**不致命**，但说明这些特征既没帮上忙也没起到"泄漏"作用，留着只是低效 |
| `cruise_time_pct` | 既在作业基线内（未列入 `DRIVING_FEATURES`），又在 `detect_faults` 里被当作**驾驶行为证据**使用（`TH["cruise_lo"]`） | 逻辑不自洽：同一特征既是"这趟活儿"又是"司机怎么开" |

**建议**：把 `speed_band_*_pct` 与 `cruise_time_pct` 明确归入 `DRIVING_FEATURES`（或反之，从规则证据里移除 `cruise_time_pct`），并说明取舍理由。**并如实记录实验 C 的结论**——"发现疑似泄漏 → 消融验证 → 实测影响可忽略"，这本身就是很好的工程叙事。

## 7. 总体评价

这个原型的**工程质量明显高于一般参赛作品**：它真的按 DBC 逐位编码出 11 MB 报文日志、真的用 cantools 走完整解码链路、真的做了样本外交叉验证、真的把仿真器的物理自洽性问题逐条记录在案（§5.2 的"踩过的坑"表格尤其难得），而且**跨 4 个大版本的依赖依然逐位可复现**。审计中的对抗性实验（编码器正确性、可辨识性、滚阻常数、查准率稳健性）**大部分未能推翻其结论**——这在第三方审计中是相当好的成绩。

问题集中在**"文档口径超出代码实现"**这一类：方案文档把"设计意图 / 后续规划 / 近似方法"写成了"已实现 / 已实测"。`prototype/README.md` 在这方面明显更诚实（它会写"单参考点 SHAP 近似"、"按定义闭合"、"精度未在仿真中单独评测"），而 `方案文档/01、02、03` 在转述时丢失了这些限定语——**尤其是 `02` 的演讲逐字稿**。

**核心判断**：这份交付的科学内容是**扎实的**，风险是**表达上的**。把 §5 的 P0 五项改完（预计半天工作量），路演的可信度会有实质性提升，而且不需要动任何算法。反过来，如果带着"我实现了 RLS 和卡尔曼融合"上台而被追问，"是否真的用了 AI"这一评审项可能会反噬。
