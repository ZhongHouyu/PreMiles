> **一句话方案**：把车队每天都在产生、却只用来"回放和报警"的整车 CAN 报文，通过一套自动化流水线翻译成**可对账的能耗账本 + 可解释的能耗拆解 + 可执行的节油建议**，用 AI 完成过去需要资深标定工程师数天才能做完的能耗诊断。

## 1. 背景与痛点

### 1.1 数据现状

商用车的车联网终端（T-Box / CAN 记录仪）以 **10~100 Hz** 采集整车 CAN / SAE J1939 报文，内容包括：

- 动力系统：发动机转速、喷油率、扭矩百分比、电机转速/扭矩、电池电压电流 SOC
- 行驶状态：车速、加速度、挡位、油门开度、制动开关、驻车制动
- 里程与位置：总里程、经纬度、海拔、方向
- 载荷与环境：轴荷/悬架压力、环境温度、胎压

一台车一天可产生 **GB 级原始报文**。这些数据目前的应用基本停留在两个层面：**实时监控大屏** 和 **故障回放**。

### 1.2 五个真实痛点

| # | 痛点 | 具体表现 |
|---|---|---|
| P1 | **数据与业务之间隔着"翻译"** | 报文里是 `0x0CF00400`、`SPN 183`，业务方只会问"这车为什么费油" |
| P2 | **能耗高但归因不了** | 只知道百公里油耗 32L，不知道其中多少耗在怠速、多少耗在顶风、多少是驾驶习惯 |
| P3 | **对比不公平，结论不可信** | 山区重载和城配空载直接比油耗，一定得出错误结论，反而引发司机抵触 |
| P4 | **异常发现靠人盯** | 喷油器衰减、刹车拖滞、胎压不足、电机效率下降，往往等到故障码亮起才发现，能耗损失已经发生几个月 |
| P5 | **分析人力不可扩展** | 一次完整的能耗分析需要：解码 → 对齐 → 算里程 → 算油耗 → 切工况 → 做 PPT，单台车单日 4 小时以上，无法覆盖车队 |

### 1.3 为什么现在能用 AI 解决

1. **数据已经在了** —— 增量成本几乎为零，这是"快速落地"的前提。
2. **物理模型 + 机器学习互补** —— 能耗有明确的物理规律（能量守恒），AI 不需要从零学物理，只需学"残差"（实际减去理论的那部分），样本需求大幅降低，且结果可解释。
3. **LLM 补齐最后一公里** —— 结构化的数字结论由大模型翻译成业务语言，直接产出可发给车队长和司机的报告。

## 2. 目标与衡量指标

### 2.1 业务目标

1. 让**任何一台车、任何一天**的能耗都能被自动拆解到"分项归因"级别；
2. 让**能耗异常**在造成更大损失之前被自动发现并推送；
3. 让**节能建议**具体到"哪个司机、哪条线路、哪个驾驶动作、预计能省多少"。

### 2.2 可量化指标（KPI）

| 类别 | 指标 | 目标值 | 验证方式 |
|---|---|---|---|
| 数据 | 报文解码成功率 | ≥ 99.5% | 解码失败帧计数 |
| 数据 | 单日数据端到端处理时延 | < 3 min / 车 / 天 | 流水线计时 |
| **精度** | 能耗与加油/充电记录**对账误差** | **< 5%** | 与加油小票、充电订单比对 |
| 精度 | 里程计算误差 | < 2% | 与里程表差分、GPS 里程三方比对 |
| **效率** | 单车单日分析耗时 | 4 h → **< 3 min** | 人工基线 vs 自动化计时（提效 > 80×） |
| 效率 | 车队周报产出 | 3 人天 → 0（自动） | 周报生成日志 |
| 智能 | 能耗异常事件查准率 | ≥ 80%（人工复核） | 抽检 50 条事件 |
| 智能 | 节油潜力测算偏差 | 与实际节油效果偏差 < 30% | 整改前后对比 |
| 业务 | 单车百公里能耗下降 | **3% ~ 8%** | 整改前后同工况对比 |

> **给评审的关键点**：效率指标（80× 提效）和精度指标（对账误差 < 5%）是"工作质量与效率"的直接证据，且都能现场演示验证。

## 3. 数据基础

### 3.1 数据来源

| 来源 | 内容 | 采样率 | 作用 |
|---|---|---|---|
| 整车 CAN / J1939 报文 | 动力、行驶、能量流信号 | 10~100 Hz | **主数据源** |
| GNSS 轨迹 | 经纬度、海拔、速度、方向 | 1 Hz | 坡度估计、里程校验、线路画像 |
| 载重 / 悬架压力 | 轴荷、总重 | 1~10 Hz | 质量估计（能耗第一敏感因子） |
| 环境 | 温度、胎压 | 0.1~1 Hz | 风阻/滚阻修正、异常归因 |
| 业务系统 | 加油小票、充电订单、运单、调度单 | 事件级 | **对账基准（真值）** |

### 3.2 关键信号清单（示例，需按实际 DBC 映射）

**燃油车**

| 信号 | 典型来源 | 单位 | 用途 |
|---|---|---|---|
| `WheelBasedVehicleSpeed` | J1939 PGN 65265 / SPN 84 | km/h | 里程、动力学 |
| `EngineSpeed` | PGN 61444 / SPN 190 | rpm | 功率计算 |
| `ActualEnginePercentTorque` | PGN 61444 / SPN 513 | % | 扭矩法反算功率 |
| `EngineFuelRate` | PGN 65257 / SPN 183 | L/h | **油耗主信号** |
| `TotalFuelUsed` | PGN 65257 / SPN 250 | L | **对账基准** |
| `AcceleratorPedalPosition` | PGN 61443 / SPN 91 | % | 驾驶行为 |
| `BrakeSwitch` | PGN 65265 / SPN 597 | 0/1 | 制动识别 |
| `SelectedGear` | PGN 61445 | — | 挡位合理性 |
| `HighResolutionTotalVehicleDistance` | PGN 65217 / SPN 917 | km | 里程校验 |

**新能源车**

| 信号 | 单位 | 用途 |
|---|---|---|
| `BatteryVoltage` / `BatteryCurrent` | V / A | **电能主信号** P = U·I |
| `StateOfCharge` | % | SOC 对账（ΔSOC 校验） |
| `MotorSpeed` / `MotorTorque` | rpm / N·m | 电驱功率与效率 |
| `RegenBrakeTorque` | N·m | 能量回收量化 |
| `MotorTemperature` / `BatteryTemperature` | °C | 热管理损耗、效率修正 |
| `AuxiliaryPower` (空调/加热) | kW | 附件能耗（电车冬季大头） |

### 3.3 数据质量现实（必须正视）

| 问题 | 影响 | 应对 |
|---|---|---|
| 丢帧 / 总线负载抖动 | 信号时间轴有洞 | 质量评分 + 插值/物理模型补全 |
| 时间戳漂移（设备本地时钟） | 多源无法对齐 | 与 GNSS UTC 对齐，估计并补偿时钟偏置 |
| 信号分辨率低（如 `TotalFuelUsed` 步进 0.5 L） | 短行程对账误差大 | 长窗口对账 + 多信号交叉验证 |
| DBC 不完整 / 保密 | 部分信号解不出 | J1939 标准 PGN 反查 + 逆向解析 + 物理量反推 |
| 单位与符号约定不统一 | 计算出负数/量级错误 | 单位注册表 + 量纲断言 + 自动异常告警 |
| 信号缺失（低配车型） | 关键量算不出 | 冗余估计（见 4.6） |

### 3.4 数据安全与合规

- 司机个人信息（姓名、工号）**与车辆数据分离存储**，分析侧只使用匿名 ID，展示层按权限回填；
- 原始报文按"热 30 天 + 冷归档 1 年"分层存储，脱敏后可用于模型训练；
- 对外汇报只出聚合结论，不出现可定位到个人的轨迹细节。

## 4. 技术方案

### 4.1 总体架构

```
┌─────────────────────────────────────────────────────────────────────┐
│ ① 采集接入层   T-Box / CAN记录仪 ── MQTT/Kafka ── 断点续传 + 去重     │
├─────────────────────────────────────────────────────────────────────┤
│ ② 存储层       原始报文(对象存储, Parquet/Blf)  +  时序库(TDengine)   │
│                 +  分析库(ClickHouse/DuckDB, 列存, 秒级聚合)          │
├─────────────────────────────────────────────────────────────────────┤
│ ③ 解析与治理层  DBC/J1939 解码 → 时间对齐 → 重采样(10Hz) → 清洗       │
│                 → 质量评分 → 单位归一 → 信号补全                      │
├─────────────────────────────────────────────────────────────────────┤
│ ④ 特征与模型层  物理能耗模型(能量守恒)  →  工况切分  →  特征工程      │
│                 →  AI 基线预测(GBDT)  →  残差异常检测(IsolationForest)│
│                 →  驾驶行为评分  →  车况衰减(CUSUM)                   │
├─────────────────────────────────────────────────────────────────────┤
│ ⑤ 应用层       能耗看板 / 单车体检报告 / 异常预警 / 节油排行          │
│                / LLM 诊断报告生成 / 调度与线路优化建议                │
└─────────────────────────────────────────────────────────────────────┘
```

**技术选型**（全部为成熟开源组件，降低落地风险）

| 环节 | 选型 | 理由 |
|---|---|---|
| 报文解码 | `cantools` + `python-can`（原型已验证） | 工业标准 DBC 解析 |
| 计算引擎 | Python (pandas/numpy) → 规模化后 PySpark | 单车用 pandas 足够快，车队上 Spark |
| 时序存储 | TDengine / InfluxDB | 高写入吞吐，降采样查询 |
| 分析库 | ClickHouse / DuckDB | 列存聚合快，支持 SQL 自助分析 |
| 机器学习 | scikit-learn → LightGBM/XGBoost | 树模型对表格特征最强、可解释 |
| 可解释性 | SHAP | 逐条结论可归因 |
| 报告生成 | LLM（结构化 Prompt） | 数字 → 业务语言 |
| 可视化 | ECharts / matplotlib | 看板与静态报告 |

### 4.2 处理流水线（核心 8 步）

1. **解码**：DBC 定义 → 物理值；未知 ID 走 J1939 标准 PGN 反查表；记录解码失败率。
2. **对齐**：全部信号统一到 **UTC + 10 Hz 网格**（连续量线性插值、累计量零阶保持、开关量就近取值，按信号类型选择），GNSS 作为时间基准。
3. **清洗**：物理量纲断言（车速 0~160 km/h、转速 0~2600 rpm、燃油率 0~200 L/h 等）、常量段识别（传感器卡死）。
4. **质量评分**：每车每日输出 0~100 分（解码成功率、缺失率、最长数据空档、信号卡死、越量程点，按**信号重要度加权**），低分数据自动标注"结论置信度低"。
5. **里程与能耗计算**：见 4.3、4.4，并要求**三条独立路径互相校验**。
6. **工况切分**：见 4.5，把行程切成怠速/起步/巡航/爬坡/制动等片段。
7. **特征工程**：片段级 + 行程级特征（见 4.7）。
8. **建模与产出**：基线预测 → 残差 → 异常 → 评分 → 报告。

### 4.3 里程计算（三条路径交叉校验）

| 路径 | 方法 | 特点 |
|---|---|---|
| A. 车速积分 | `s = ∫ v dt`，梯形法 | 连续，但有累积误差 |
| B. 里程表差分 | `Δ(TotalVehicleDistance)` | 最准，但分辨率有限 |
| C. GNSS 累积 | 相邻点大圆距离之和 | 独立第三方，但隧道/城市峡谷丢星 |

**融合策略**：以 B 为主，A 做高频细分，C 做异常检测。三者两两偏差 > 2% 时告警并降级标注。

### 4.4 能耗模型（本方案的物理内核）

#### 4.4.1 燃油车：化学能 → 车轮

燃油低热值取 **LHV = 42.8 MJ/kg，密度 0.84 kg/L → 35.95 MJ/L ≈ 9.99 kWh/L**（可按实测油品标定）。

**（1）主算法 —— 燃油率积分**
```
E_fuel[L] = ∫ EngineFuelRate[L/h] dt / 3600
E_chem[kWh] = E_fuel × 9.99
```

**（2）对账算法 —— 累计油耗差分**
```
E_fuel_ref[L] = TotalFuelUsed(t_end) − TotalFuelUsed(t_start)
```
> 两条路径偏差 > 5% 时，说明 ECU 燃油率信号或数据质量有问题，自动标记。

**（3）补全算法 —— 扭矩法**（燃油率信号缺失时）
```
P_e[kW] = T_e[N·m] × ω[rad/s] / 1000
T_e = ActualEnginePercentTorque% × 额定扭矩
BSFC = f(n, T_e)        # 万有特性 MAP 查表, g/kWh
FuelRate[L/h] = P_e × BSFC / 1000 / 0.84
```

#### 4.4.2 新能源车：电池 → 车轮

```
P_batt[kW] = U[V] × I[A] / 1000        # 放电为正, 回收为负
E_batt[kWh] = ∫ P_batt dt
```
**对账**：`ΔSOC × 额定电量 × 额定电压` 应与 `E_batt` 一致，偏差 > 5% 告警。
**注意**：需区分**驱动能耗**与**附件能耗（空调/加热）**，冬季电车附件可占 20~35%。

#### 4.4.3 纵向动力学能耗分解（可解释的关键）

整车纵向受力：

```
F_total = m_eff·a  +  m·g·sinθ  +  m·g·C_rr·cosθ  +  ½·ρ·C_d·A·(v + v_wind)²
          └ 惯性 ┘   └ 坡道 ┘    └── 滚动阻力 ──┘   └──── 空气阻力 ────┘
m_eff = m · (1 + δ)      δ ≈ 0.04~0.10（旋转惯量等效系数）
```

车轮处需求功率：`P_wheel = F_total · v`

传动与能量转换：
```
驱动:  P_engine = P_wheel / η_drivetrain + P_aux
制动:  P_brake_loss = |P_wheel| × (1 − η_regen)     # 燃油车基本全部耗散
```

**能耗瀑布（The Energy Waterfall）** —— 把化学能/电能逐项拆开：

```
E_chem  =  E_idle      怠速耗能
         + E_aux       附件（空调/加热/取力器）
         + E_roll      滚动阻力
         + E_aero      空气阻力
         + E_grade     坡道（上坡为正, 下坡回收为负）
         + E_kinetic   净加速（动能变化, 可正可负）
         + E_brake     制动耗散
         + E_dt_loss   传动损失 (1−η)
         + ε           模型残差（应 < 5%）
```

> **这张瀑布图就是"能耗高在哪"的答案**，也是本方案最有说服力的输出：一个数字变成一堆可归因的分项，而且各项之和必须回到总量（能量守恒自检）。

#### 4.4.4 三个难点的工程解法

| 难点 | 解法 |
|---|---|
| **整车质量 m 未知** | ① 轴荷/悬架压力传感器直接读数；② 无传感器时用**递推最小二乘（RLS）质量辨识**：在加速段用 `m̂ = (F_drive − F_resist)/a` 递推估计，配合工况筛选（|a| > 0.3 m/s²、无换挡、无制动）保证收敛 |
| **道路坡度 θ 未知** | ① GNSS 海拔差分（噪声大，需低通）；② 气压高度计；③ **卡尔曼滤波融合**：把 `a_GNSS − a_车速` 的差值作为坡度观测量，与海拔差分融合，输出平滑坡度 |
| **风速/风阻** | 无风速传感器时按 `v_wind = 0` 处理并做**标定**：用长期巡航段数据反标 `C_d·A`，把系统偏差吸收进气动系数，避免引入不可观测变量 |

### 4.5 工况切分（Operating Mode Segmentation）

**方法**：规则状态机（可解释、可审计）+ 无监督聚类（发现未知模式）双轨。

| 工况 | 判定条件（示例） | 关注点 |
|---|---|---|
| 怠速 | v < 1 km/h 且发动机/电机运行 | 怠速时长占比、怠速油耗率 |
| 起步/加速 | a > 0.3 m/s² | 大油门起步次数 |
| 匀速巡航 | \|a\| < 0.2 m/s² 且 v > 40 km/h | 经济车速达成率 |
| 减速/制动 | a < −0.3 m/s² 或制动开关 = 1 | 制动能量耗散、可否回收 |
| 爬坡 | θ > 1.5% | 挡位选择是否合理 |
| 下坡 | θ < −1.5% | 是否用发动机制动/能量回收 |
| 停车熄火 | v = 0 且转速 = 0 | 长时间怠速不熄火 |

**聚类补充**：对片段的速度-加速度-坡度三维轨迹做 KMeans / DTW 聚类，自动发现"高频启停的城配工况""长时间高速满载工况"等，用于线路画像。

### 4.6 信号缺失时的冗余估计

| 缺失信号 | 估计方法 |
|---|---|
| 燃油率 | 扭矩法（4.4.1-3） |
| 坡度 | 卡尔曼融合（4.4.4） |
| 质量 | RLS 辨识（4.4.4） |
| 车速 | GNSS 速度 / 轮速信号 |
| 电池电流 | 电机功率 / 效率 MAP 反推 |

### 4.7 AI 建模层（本方案的"智能"部分）

#### 模型 1：能耗基线预测（核心）

- **任务**：给定"这台车、这条线路、这个载重、这个天气、这种工况"，预测**应该**消耗多少能耗。
- **输入特征**（片段级 + 行程级聚合）：

| 特征组 | 具体特征 |
|---|---|
| 速度 | 平均/最高车速、车速分布熵、各速度带时间占比 |
| 驾驶激烈度 | 正加速度均值（PKE，正动能需求）、急加速/急减速次数、油门开度标准差 |
| 怠速 | 怠速时长占比、怠速次数 |
| 线路地形 | 累计爬升/下降、平均/最大坡度、坡度分布 |
| 载荷 | 平均/最大载重、载重利用率 |
| 环境 | 平均温度、空调使用时长 |
| 车辆 | 车型、车龄、总里程、动力型式 |
| 时段 | 早晚高峰占比 |

- **模型**：`HistGradientBoostingRegressor`（原型已用）/ 生产用 LightGBM。目标变量：`L/100km` 或 `kWh/100km`，标签按车型+线路分层。
- **输出**：预测值 + **残差** `r = 实际 − 预测`。
  - `r ≈ 0` → 正常
  - `r > 0`（显著）→ **这台车这段行程，比同类应该的水平更耗能** → 进入归因
  - `r < 0` → 优秀，可提取其驾驶/操作特征作为标杆推广

> **关键设计**：基线模型同时是**公平比较器**。它把"山区重载"和"城配空载"拉到了同一条起跑线上，解决了痛点 P3。这也是司机愿意接受这套系统的前提。

#### 模型 2：能耗异常检测

两条腿走路，互补：

1. **残差异常（统计）**：残差 z-score > 2.5 持续 N 段 → 可疑
2. **无监督异常（IsolationForest）**：在"片段特征 + 物理残差"空间上找离群点，无需标签

**可识别的典型异常**（这是业务最买账的部分）：

| 异常类型 | 在数据上的特征 |
|---|---|
| 喷油器/燃烧恶化 | 整体能效反标定值系统性偏低（同工况燃油率偏高、扭矩法 vs 燃油率法偏差变大） |
| 刹车拖滞 / 轮毂轴承 | 整体能效偏低 + **无制动时仍有异常减速阻力**（滑行段反标定滚阻） |
| 胎压不足 | 整体能效偏低 + **胎压信号偏低**（唯一能与"燃烧恶化"区分的独立观测量，见下） |
| 空气滤芯堵塞 / 进气异常 | 同转速扭矩下降，燃油率相对升高 |
| 电机效率衰减 | 同扭矩转速下 `P_batt` 升高，`P_batt/P_wheel` 效率下降 |
| 电池一致性/内阻升高 | 充电时间变长、同 SOC 区间压降变大 |
| 长时间怠速不熄火 | 每百公里怠速秒数（距离归一化）突增 |
| 恶劣驾驶 | 平均车速/风阻能耗高于同线路同车型司机、急加速/急减速率偏高 |
| 空调/加热异常耗电 | 附件能耗占比与温度关系偏离正常曲线 |

> ⚠️ **必须正视的可辨识性边界（原型实测结论）**：
> 分析侧永远按铭牌滚动阻力系数计算，因此"滚动阻力能耗"在所有车次上是**常数**，
> **不能**作为滚阻故障的检测器；而"胎压不足"与"燃烧恶化"的整体能效反标定值
> 几乎完全相同（实测 0.3122 vs 0.3125）——**仅凭油耗数据二者本质不可辨识**。
> 因此方案的做法是：**先给出两个候选假设，再用独立观测量判别**。
> 有胎压信号就用胎压信号；没有的车型必须做**滑行试验（coast-down）反标定滚阻**，
> 否则系统只能说"能耗偏高，原因待查"，不应武断归咎于车辆。

#### 模型 3：驾驶行为评分与节油潜力

```
DriverScore = 100 − w₁·norm(残差百分位)
                   − w₂·norm(急加速+急减速千公里次数)
                   − w₃·norm(怠速时长占比)
                   − w₄·norm(经济车速偏离度)
```
用 **SHAP** 给出每位司机每条扣分的具体来源 → 生成"该司机本月能耗高于基线 6.2%，其中 3.1% 来自急加速、1.8% 来自超速巡航、1.3% 来自怠速"这类**可直接沟通**的结论。

#### 模型 4：车况衰减趋势监控

对同一台车（或同一司机+同一线路）的残差序列做 **CUSUM 变点检测**。残差均值发生持续上移 → 提示"该车技术状况正在劣化，建议进站检查"，把故障发现提前到故障码之前。

#### 模型 5：LLM 诊断报告生成

把上述结构化结果（能耗瀑布、残差、异常项、SHAP Top-5、对账结果）按固定 JSON Schema 交给大模型，生成：

- 面向**车队管理者**的《车辆能耗体检报告》
- 面向**司机**的《一对一驾驶改进建议》（措辞正向激励）
- 面向**维修**的《疑似技术状况问题工单》

**约束**：LLM 只做"翻译与表达"，**所有数字由物理模型和统计模型计算**，禁止 LLM 生成或推算数值 —— 通过 Prompt 硬约束 + 输出数值校验（正则提取后与源数据比对）保证。

### 4.8 可解释性与对账闭环（质量保证机制）

```
物理模型给"应该多少"  ──┐
实测信号给"实际多少"  ──┼──► 残差 ε ──► ε > 5% ? ──► 触发：数据质量告警 / 信号核对
加油充电记录给"真值"  ──┘                                  / 模型参数重标定
```

**每一份报告都必须通过三道自检才能发布**：
1. **能量守恒自检**：瀑布图各分项之和 = 总能耗（误差 < 3%）
2. **三方里程自检**：积分/里程表/GNSS 两两偏差 < 2%
3. **对账自检**：与加油/充电记录偏差 < 5%

> 这三道自检是本方案区别于"跑个模型出个图"的关键 —— 它让结论**敢拿去和车队对账**。

本方案附带一个**可运行的端到端原型**，位于 `prototype/`，用于证明技术路线可行、并作为现场演示的载体。

**原型能力**

| 模块 | 文件 | 说明 |
|---|---|---|
| DBC 定义 | `config/trucks_demo.dbc` | J1939 风格 DBC（11 条报文 / 25 个信号），由 `src/dbc_spec.py` 数据字典渲染 |

| 清洗与质量 | `src/preprocess.py` | 重采样 10 Hz、量纲断言、质量评分、插值补全、坡度/质量估计 |
| 能耗模型 | `src/energy.py` | 里程三路径、能耗主算法、**能量瀑布分解**、三道自检对账 |
| 工况与评分 | `src/modes.py` | 工况切分、驾驶行为量化与评分 |
| AI 模型 | `src/ai_models.py` | 基线预测（GBDT）+ 样本外残差 + IsolationForest + 物理规则判据 + 责任判定 + CUSUM |
| 报告 | `src/report.py` | 4 张图表 + Markdown 体检报告（LLM 输入就绪） |
| 编排 | `run_demo.py` | 一键端到端 |

**原型验证结果（`python run_demo.py` 实测，可现场复现）**

| # | 验证项 | 目标 | **实测结果** |
|---|---|---|---|
| 1 | 报文解码成功率 | ≥ 99.5% | **100.0000%**（235,711 帧 / 3 车次 / 11 MB） |
| 2 | 能耗 vs 仿真真值误差 | — | **0.01% ~ 0.05%** |
| 3 | 三方里程最大互差 | < 2% | **0.01% ~ 0.21%** |
| 4 | **与加油记录对账误差** | **< 5%** | **1.08% ~ 3.57%** |
| 5 | 能量瀑布守恒自检残差 | < 3% | **~1e-14%（浮点零）** |
| 6 | 单车能耗分析耗时 | < 3 min | **0.04 s** |
| 7 | 能耗基线模型（样本外） | — | **R² = 0.894，MAPE = 4.61%**（MAE 1.71 L/100km） |
| 8 | 异常检测 | — | **查准率 100%、查全率 79.2%、F1 0.884**（56 个正常车次**零误报**） |

> **一个必须说清的口径**：第 2 行的 0.01%~0.05% 指的是**能耗账目本身**
> （燃油升数 / 化学能总量）与真值的偏差 —— 这是"账算得准不准"。
> 而**车轮侧物理分解**（滚阻/风阻/坡道各占多少）是按**铭牌参数**算的：
> 遇到滚阻实际恶化 35% 的车次，分解结果与真值会差 **9%~17%**。
> 这不是缺陷，**这恰恰是 AI 要检测的信号** —— 分解对不上，说明车辆参数变了。
> 也正因如此，报告里"与真值对照"一栏在故障车次上会明显偏大，
> 而"三道自检"（能量守恒 / 三方里程 / 加油对账）依然全部通过。

**故障类型 × 系统责任判定**（最能说明 AI 有效性的一张表）：

| 注入故障 | 平均残差 | 未标记 | 待人工判定 | 车辆状况主导 | 驾驶行为主导 | 共同作用 |
|---|---:|---:|---:|---:|---:|---:|
| 燃烧恶化 | +9.9% | 0 | 0 | **3** | 0 | 1 |
| 胎压不足 | +6.5% | 0 | 0 | **6** | 0 | 2 |
| 激烈驾驶（超速） | +2.6% | 5 | 1 | 0 | **2** | 0 |
| 长时间怠速 | −1.4% | 0 | 0 | 0 | **4** | 0 |
| 正常 | −2.3% | **56** | 0 | 0 | 0 | 0 |

> 车辆类故障被判为"车辆状况主导"，驾驶类故障被判为"驾驶行为主导" ——
> 直接回答业务最关心的问题："这台车费油，是车的问题还是司机的问题？"
> 查不出单一原因的车次判定为**「待人工判定」**，**不**武断归咎于车辆。

**一个值得写进方案的可辨识性结论**：分析侧永远按铭牌滚动阻力系数计算，
因此"滚动阻力能耗"在所有车次上是常数，**不能**作为滚阻故障的检测器；
而胎压不足与燃烧恶化的整体能效反标定值几乎相同（0.3122 vs 0.3125）——
**从油耗数据出发二者本质不可辨识**。方案的处理是：给出两个候选假设，
再用**独立观测量（胎压信号）**判别。这也是原型在 DBC 中增加 `TRK_TPMS1` 的原因。

**技术细节、关键设计决策与踩坑记录**见 `prototype/README.md`
（为什么先做仿真、真值物理自洽性、特征分组如何决定残差含义、
为什么责任归属用规则而非第二个模型、已知局限）。

**为什么先做仿真再上真车**：真实数据受保密与获取周期限制，仿真数据带**真值**，可以先证明"算法算得准"；拿到真车数据后只需替换数据源，模型与流水线不变。
**仿真不能替代真车验证** —— 上述精度指标需在真实数据上重新实测，不可直接沿用。

## 10. 风险与应对

| 风险 | 可能性 | 影响 | 应对措施 |
|---|---|---|---|
| **拿不到真实报文数据**（保密/流程慢） | 中 | 高 | ① 提前走数据申请流程；② 用仿真数据先跑通全链路（原型已完成）；③ 用脱敏后的单台车样本做 PoC |
| DBC 不完整、信号解不出 | 高 | 中 | J1939 标准 PGN 反查 + 逆向解析 + 扭矩法/观测器冗余估计 |
| 数据质量差（丢帧严重） | 中 | 高 | 质量评分前置，低质量数据自动降级并标注置信度，不输出误导结论 |
| **对账误差打不进 5%** | 中 | 高 | 多算法交叉（燃油率积分/累计油耗差分/扭矩法），偏差大时自动定位是哪个信号的问题；必要时用长窗口对账 |
| 质量估计不准导致分解失真 | 中 | 中 | 优先用轴荷传感器；无传感器用 RLS 辨识 + 与总油耗做一致性校验 |
| 司机抵触"被监控" | 中 | 中 | ① 定位为**辅助工具**而非考核；② 输出正向激励与排行榜奖励；③ 个人信息脱敏；④ 用公平基线（同类同线路）对比 |
| LLM 幻觉编造数字 | 中 | 高 | 数值全部由物理/统计模型计算，LLM 仅做文字表达；输出做数值回校验，不匹配则拒绝发布 |
| 样本量不足，模型过拟合 | 中 | 中 | 先用物理模型兜底；模型用同型车/同线路分层聚合；持续积累数据后迭代 |
| 路演现场演示失败 | 低 | 高 | Demo 完全离线可运行；预先录制备份视频；准备静态报告兜底 |

| **是否符合"资料审核、数据整理、代码编写、数据分析"场景** | 本质是**数据分析 + 数据整理**场景：把不可读的原始报文整理成可读、可对账、可决策的能耗账本 |
| **是否可复制推广** | 架构与车型解耦，仅需替换 DBC 与参数集；可从商用车推广到任何有 CAN 数据的车队/设备 |
| **经济价值是否清晰** | 100 台车规模年化 **54 万 ~ 144 万元**，且不依赖新硬件投入 |

## 12. 附录

### 附录 A：核心公式汇总

| 量 | 公式 |
|---|---|
| 里程 | `s = ∫ v dt` |
| 燃油化学能 | `E_chem = E_fuel[L] × 9.99 kWh/L` |
| 电池能量 | `E_batt = ∫ U·I dt` |
| 整车质量（含旋转惯量） | `m_eff = m(1+δ)` |
| 惯性力 | `F_acc = m_eff · a` |
| 坡度阻力 | `F_grade = m g sinθ` |
| 滚动阻力 | `F_roll = m g C_rr cosθ` |
| 空气阻力 | `F_aero = ½ ρ C_d A v²` |
| 车轮需求功率 | `P_wheel = (F_acc+F_grade+F_roll+F_aero)·v` |
| 发动机功率 | `P_engine = P_wheel/η_dt + P_aux` |
| 标准能耗指标 | `L/100km`、`kWh/100km`、`L/(100 t·km)` |
| 基线与残差 | `r = 实际能耗 − 模型预测能耗` |

**典型参数取值（需按车型标定）**

| 参数 | 典型值 |
|---|---|
| 柴油低热值 LHV | 42.8 MJ/kg |
| 柴油密度 | 0.83 ~ 0.845 kg/L |
| 传动效率 η_dt | 0.88 ~ 0.93（直接挡） |
| 滚动阻力系数 C_rr | 0.006 ~ 0.010（良好路面） |
| 空气阻力系数 C_d | 0.5 ~ 0.7（重型卡车） |
| 迎风面积 A | 8 ~ 10 m² |
| 旋转惯量系数 δ | 0.04 ~ 0.10 |
| 空气密度 ρ | 1.225 kg/m³（15°C 海平面） |

### 附录 B：术语表

| 术语 | 含义 |
|---|---|
| 报文 | CAN 总线上传输的数据帧，含 CAN ID + 8 字节数据 |
| DBC | 描述 CAN 报文中各信号位置、精度、单位的定义文件 |
| J1939 | 商用车 CAN 应用层标准，用 PGN/SPN 定义参数 |
| PGN / SPN | 参数组编号 / 可疑参数编号 |
| 跟车报文 | 车载终端随车采集并回传的整车报文数据 |
| PKE | 正动能需求（Positive Kinetic Energy），驾驶激烈度指标 |
| BSFC | 有效燃油消耗率，g/kWh |
| CUSUM | 累积和变点检测方法 |
| SHAP | 基于博弈论的模型可解释性方法 |
| VSP | 车辆比功率，常用于工况与排放分析 |

### 附录 C：原型运行方式

```bash
cd prototype
pip install -r requirements.txt
python build_dbc.py           # 生成并校验 DBC 数据字典（可选，run_demo 会自动生成）
python run_demo.py            # 一键端到端：仿真 → 报文字节编码 → 解码 → 能耗 → AI → 报告
python run_demo.py --quick    # 快速模式（约 25 秒），用于彩排
python run_demo.py --powertrain ev   # 切换纯电车型
```

* 全程**离线**、单进程、无 GPU；完整模式约 **70 秒**跑完 80 车次。
* 结果**可复现**（随机种子由 `stable_seed` 固定，不使用 Python 内置 `hash()`）。
* 产物输出到 `prototype/outputs/`：4 张图表、单车体检报告、车队汇总 CSV、
  异常清单 JSON、归因示例 JSON、完整运行日志 `run_log.txt`。
* 设计说明、实测指标与**踩坑记录**见 `prototype/README.md`。

### 附录 D：待确认信息（向客户/业务方确认）

为把方案从"可行"推进到"落地"，需要确认：

1. **车队动力型式**：燃油 / 纯电 / 混动？占比？
2. **数据可得性**：能否提供 ≥3 台车 ≥5 天的原始报文样本 + DBC？
3. **对账真值**：是否有同期加油小票 / 充电订单？（**这是精度验证的前提**）
4. **载荷信息**：是否装配轴荷/悬架压力传感器？
5. **定位精度**：GNSS 是否含海拔与速度？采样率？
6. **业务目标**：本次是"找异常"还是"建常态化能耗管理体系"？（决定做 PoC 还是做平台）
7. **数据合规**：司机个人信息的脱敏与使用边界由谁审批？
