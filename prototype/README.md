## 1. 快速开始

```bash
cd prototype

python build_dbc.py            # 生成并校验 DBC 数据字典（可选，run_demo 会自动生成）
python run_demo.py             # 完整车队：40 天 x 2 车次 = 80 车次，3 车次落地真实报文
python run_demo.py --quick     # 快速模式（12 天），用于彩排
python run_demo.py --days 60   # 扩大样本
python run_demo.py --powertrain ev   # 切换纯电车型
```

**依赖**：Python 3.9+，`numpy pandas scipy scikit-learn matplotlib cantools`
（`pip install -r requirements.txt`）。无网络、无 GPU、无外部服务依赖，全流程离线可运行。

**运行时长**（普通笔记本，单进程）：完整模式约 70 秒，快速模式约 25 秒。

## 5. 关键技术决策（以及为什么这么做）

### 5.1 为什么先做仿真，而不是等真车数据

真实报文受保密与申请周期限制。仿真数据**自带真值**，可以在拿到真车数据之前
就证明"算法算得准"。拿到真车数据后只需替换数据源，`energy.py` / `features.py` /
`ai_models.py` 一行不用改。

仿真器刻意叠加了真车的测量缺陷：信号量化、传感器噪声、随机丢帧、
**突发丢包**（隧道/总线抖动，2.5~8 秒）、GNSS 高程噪声。因此质量评分与
插值补全逻辑是**真的在被测试**，不是走过场。

### 5.2 真值必须物理自洽（踩过的坑）

初版仿真器有几个"看起来对、其实不可能"的问题，都会让精度结论失去意义：

| 问题 | 后果 | 修正 |
|---|---|---|
| 载荷没进入物理模型 | 载重对能耗毫无影响 | `simulate_trip` 把 `spec.payload_kg` 写进参数副本 |
| 只限制惯性功率 | 353 kW 卡车输出 600 kW | `solve_feasible_profile` 约束**整车**功率 |
| 单向功率限幅 | 车辆爬坡掉速后永远追不上目标曲线，里程腰斩 | 改为**闭环驾驶员模型**（一阶跟随 + 功率约束） |
| 急加速/急减速脉冲幅度不对称 | 加速被功率封顶、减速不受限，车速逐次"向下棘轮" | 脉冲幅度按该时刻可用功率缩放 |
| 坡道位置随里程平移 | 控制器依据的坡度与真值坡度不一致，约束落错位置 | 坡度-里程迭代对齐 |

> ⚠️ **2026 审计更正——上一行不成立**：第三方审计复算（`audit/audit2.py` 实验 G，80 车次全量）实测
> **发动机峰值 max = 364.2 kW、中位数 345.1 kW**，其中 **12 个车次 > 347 kW**、**6 个车次 > 额定 353 kW**、
> **61 个车次 > 仿真器自设的车轮功率上限 310.64 kW**。
> **根因已精确定位**：`simulator.solve_feasible_profile()` 在求解功率可达轨迹时**没有施加 `c_rr_scale`**
> （按铭牌 `C_rr` 算阻力），而真值能耗计算处却施加了故障倍数
> （`ph.road_load_power(..., c_rr_scale=spec.c_rr_scale)`），于是胎压不足车次（`c_rr_scale = 1.35`）
> 在求解时被放行、在算能量时被迫多输出 35% 滚阻功率——**超限最严重的 6 个车次全部是 `tire_pressure_low`**。
> **影响**：对**能耗账目精度无影响**（仍 0.00%~0.03%）；但削弱"真值物理自洽"的宣称，并会轻微放大该类车次的残差（实测 +6.5%）。
> **修复方式约 3 行**：给 `solve_feasible_profile` 增加 `c_rr_scale` 参数并在 `simulate_trip` 中传入，
> 同时补上 `f_roll` 的 `sign(v)`（该函数内注释已自陈需乘 `sign(v)`，代码只乘了 `1.0 if vi>0 else 0.0`）。

### 5.3 特征分组决定"残差代表什么"

这是整个 AI 设计的核心，也是最容易做错的地方：

* **`LEAKY_FEATURES`（防泄漏）**：由能耗物理分解直接推导出来的量
  （`roll_kwh_per_km`、`traction_kwh_per_km` 等）。放进模型就是循环论证，必须排除。
* **`DRIVING_FEATURES`（驾驶行为）**：描述"司机怎么开"的量，
  **只在作业基线模型中排除**。于是残差 = 驾驶行为 + 车辆状况 + 其他超额消耗。
* **`avg_speed_kph` / `duration_s` / `idle_time_pct` 必须排除**：
  怠速会同时压低平均车速，若把它们放进基线，模型会把"怠速多"当成"工况差"
  解释掉，怠速油耗就永远查不出来。
* **怠速改用 `idle_s_per_100km`（距离归一化）**：
  理由是**跨行程长度的可比性**——用时间百分比会被行程长短混淆。
  ⚠️ **2026 审计更正**：本节此前引用的"实测正常车次中位数 10.7%、p90 达 27%，
  与注入怠速的 30.9% 几乎无法区分"**在当前代码上不复现，已删除**。
  按权威产物 `outputs/车队汇总.csv` 复算：正常车次 `idle_time_pct` 中位数 **5.4%**、
  p90 **5.7%**、max 6.1%；注入怠速中位数 **25.2%**、min 24.5%。
  **两种口径在本仿真数据上都是完美分离**（均 4/4 检出、0/56 误报）。
  因此距离归一化的正确理由是**统计性质（跨行程可比）**，不是"本例分离度不足"。

### 5.4 三级判据 + 强证据门限 + 诚实的"查不出来"

异常判定不是单一模型输出，而是三路证据合并：

1. **物理规则**（最可解释、小样本最稳健）：怠速、超速、急加速/急减速、PKE、
   整体能效反标定、胎压
2. **统计判据**：作业基线残差 z 分数显著且为正
3. **无监督判据**：IsolationForest 离群且残差为正

规则阈值取 `max(P90, 中位数×倍数)`（高侧）或 `max(中位数×倍数, P05)`（低侧）。
**低侧刻意不用 P10** —— 当异常样本恰好占 10% 时，P10 就落在异常样本身上，
阈值等于异常值本身，规则永远无法触发（胎压规则曾因此**完全失效**）。

另外设置**强证据门限**：仅有行为规则命中、总能耗未超标、证据又不强时不告警。
没有这道门限时误报率高达 16%（9/56 正常车次被误标）。

**查不出原因时就说查不出**：早期版本把"残差为正但无物理解释"直接归为
"车辆状况主导"，这会系统性冤枉车辆。现在这类车次判定为**「待人工判定」**，
并明确说明"未定位到单一物理原因"。

### 5.5 一个重要的可辨识性结论：油耗分不清"胎压"和"燃烧"

实现过程中发现并验证了一件事，值得写进方案：

* 分析侧永远按**铭牌 C_rr**（本原型 `params.c_rr = 0.0075`）计算滚动阻力，
  所以"滚动阻力能耗"对每个车次都是常数 —— **它作为故障检测器是完全无效的**。
  初版把它当判据，等于埋了一个永远不会触发的规则。
  ⚠️ **2026 审计更正**：`crr_est` / `cda_est` 这两个变量**在整个原型中从未被赋值**
  （只出现在 `features.LEAKY_FEATURES` 的排除名单里，从未进入产物 CSV），
  此前"实测 `crr_est` 恒为 0.02040"的表述**名称与物理含义都写错了**。
  0.02040 的真实身份是**每吨公里滚阻能耗**：复算 `roll_kwh_per_km / mass_t` 为
  **0.02042 ~ 0.02043 kWh/(t·km)**，相对离散仅 **0.003%**，与理论值
  `g·C_rr·1e6/3.6e6 = 0.02044` 一致（审计实验 M）。
  **结论本身不变**（恒为铭牌常数 → 不能作滚阻故障检测器），只是数字的名称与出处已更正。
* 真正有用的是**整体能效反标定**
  `eta_engine_est = 牵引侧机械功 / 可用于牵引的燃油化学能`（分子分母都剔除怠速）。
* 但胎压不足与燃烧恶化的 `eta_engine_est` **几乎完全相同**
  （实测中位数 0.3122 vs 0.3125）—— 从油耗数据出发，二者**本质不可辨识**，
  因为"阻力变大"和"效率变低"都表现为同样的油耗上升。

因此方案的处理方式是：先给**两个候选假设**，再用**独立观测量（胎压信号）**判别。
这也是为什么原型在 DBC 里加了 `TRK_TPMS1` 报文 —— 不是为了让规则好写，
而是因为**没有它就无法区分这两类故障**。真实项目里同理：
要么有胎压信号，要么就得做滑行试验（coast-down）反标定滚阻。

### 5.6 责任归属用规则而不是第二个模型

曾尝试"双基线"（模型 A 不含驾驶特征、模型 B 含），用 `残差A − 残差B` 拆分责任。
在 80 样本下模型 B 的样本外 R² 反而更低（0.700 vs 0.742），拆分结果是噪声。
**宁可不给，也不给错** —— 最终改为按证据类型判定，稳健且完全可解释。
样本量上到几千条后可以再切回模型拆分。

### 5.7 数值全部由物理/统计模型计算，模板不编造

`report.py` 只做模板渲染，所有数字来自 `EnergyResult` 与模型输出。
生产环境接 LLM 时保持同样的约束：LLM 只负责把结构化结论翻译成自然语言，
输出需做数值回校验后才允许发布。

## 7. 已知局限（如实说明）

1. **异常检出查全率 79.2%**：`aggressive_driving` 仅检出 3/8 —— 注入的超速
   被功率可达性约束部分抵消，实际车速差异只有约 +6%，低于判据阈值。
   真实场景应结合维修工单做闭环回流，持续降低漏报。
   ⚠️ **口径更正**：该 79.2% 为**全量自评口径**（`detect_faults` 的规则阈值取自被评测的同一批数据）。
   第三方审计做折半交叉验证（阈值只在半数样本上标定、在另半数评估，5 次随机折半）后，
   **查全率为 70.8%**；而**查准率 100% 在 5 次折半下依然稳健**（56 个正常车次零误报）。
2. **胎压与燃烧恶化从油耗上不可辨识**（见 5.5）：必须依赖独立观测量。
   原型靠 `TRK_TPMS1` 区分；无胎压信号的车型需要滑行试验反标定滚阻。
3. **对账精度受累计油耗分辨率限制**：`TotalFuelUsed` 为 0.5 L/bit，
   短行程的量化下限本身就可达 4%~6%（报告中对每个车次都给出了该下限）。
   真实场景应与加油周期（而非单次行程）对账。
4. **质量与坡度依赖传感器（⚠️ 2026 审计更正，此处此前表述与代码不符）**：
   `preprocess.estimate_mass` 只在**有**轴荷/悬架信号（`TotalVehicleMass`）时取其滑动平均；
   **无信号时返回"不可用"，`energy.analyze_frame` 会静默回退到铭牌质量 `params.mass_kg()`——
   不报错、不标记降级**。这是已定位缺陷：对重载变化的场景，它会系统性污染整条瀑布分解与残差。
   **递推最小二乘（RLS）质量辨识并未实现**（全仓库 `RLS|递归最小二乘|recursive_least` 在 `.py` 中零命中）。
   坡度侧：IMU 5 s 滑动平均优先、GNSS 高程 30 s 窗口线性回归**回退**（`if/elif`），
   **这是回退而不是融合，卡尔曼滤波未实现**。
   待办：补约 40 行 RLS 辨识（加速段 `m̂ = (F_drive − F_resist)/a` + 工况筛选），
   并在走静默回退时**强制降低质量分并标注置信度**。
5. **风阻未做风速补偿**：风速传感器缺失时按 `v_wind = 0` 处理，
   系统偏差被吸收进气动系数标定。
6. **仿真 ≠ 真实**：仿真能证明算法**自洽且算得准**，
   不能替代真车数据上的验证。
7. **仿真车队工况高度同质，R²/MAPE 偏乐观**：`avg_speed_moving_kph` 相对离散仅 **2.9%**、
   `distance_km` **2.4%**（只有 `payload_t` 有 23.9% 的离散），因为所有车次共用同一套
   30 分钟工况骨架。审计复算显示：**单特征（整车总质量）R² 就有 0.797**，
   **载荷+地形 4 特征为 0.909**（高于文档 14 特征口径的 0.894）。
   真实车队的城市配送 vs 干线长途差异远大于此，因此本原型给出的
   基线模型指标**相对真实项目偏乐观**，必须在真实数据上重新标定。
8. **"三道自检"不能验证物理模型算得对**：审计实验 A 用故意错标的整车参数重算同一份报文日志——
   `C_rr`×3 使牵引能耗从 26.87 kWh 变成 **42.06 kWh（+56.5%）**，
   而守恒残差、车轮恒等式、里程互差、对账误差**全部通过**。
   原因是：守恒项是**配平项**（按定义闭合，残差恒为 0，`passed=True` 是硬编码），
   车轮恒等式是代数恒等式，里程与对账只依赖报文信号、与整车参数无关。
   **结论**：它们只验证"报文链路与账目自洽"。物理正确性必须靠**独立观测量**
   （地磅称重、滑行试验反标 `C_rr`、长巡航段/风洞反标 `C_d·A`、台架 BSFC MAP）。
9. **检出主力是物理规则，不是统计模型**：全系统 19 条标记中，纯统计判据
   （`z ≥ 1.8` 且残差 > 1.5%）只贡献 **3 条**（单独使用查全率仅 **12.5%**）。
   这符合 §5.4 "物理规则最可解释、小样本最稳健"的设计取向，
   但对外不应表述为"AI 模型承担了主要检出工作"——AI 的主要贡献在**公平基线与归因**。
10. **近邻基线里混有故障车**：每个车次的 9 个近邻中故障样本占比**均值 22.2%、最大 56%**
    （车队整体故障比例 30%），会抬高基准、压低偏差——`tire_pressure_low` 的同类偏差
    只有 **+2.55%**，而其模型残差为 **+6.48%**。
    待办：计算近邻中位数时剔除已被标记为异常的车次（迭代一次即可）。
11. **"CAN ID 命中率"不度量信号完整性**：审计实验 J 破坏 5% 帧的载荷字节后，
    该指标仍为 **100.0000%**（DBC 未定义 CRC，`cantools.decode_message` 对任意 8 字节都能"成功"解出数值）；
    只有注入未知 CAN ID 才会下降（99.3682%）。真正兜住损坏数据的是
    `score_quality` 的量程断言（`RANGE_CHECK`）与卡死检测。
    **接入真车 DBC 前必须确认是否存在 CRC/校验字段。**
12. **中文 Windows 控制台编码**：控制台默认代码页为 GBK 时，
    `run_demo.py` 在打印 `R²` 处会抛 `UnicodeEncodeError` 并中断在 AI 层之前。
    运行前请 `chcp 65001` 或设置 `$env:PYTHONIOENCODING="utf-8"`
    （已在 Python 3.12.10 + 中文 Windows 上按此设置完整跑通，端到端 **6.8 s**，
    全部指标与 §3 一致）。

## 8. 故障注入说明（仅仿真专有）

为量化 AI 效果，仿真器按 30% 比例注入四类故障，并保留真值标签用于评测：

| 故障 | 注入方式 | 实测能耗代价 | 检出率 |
|---|---|---:|---:|
| `tire_pressure_low` | 滚动阻力系数 × 1.35（同时胎压降至 615 kPa） | +9.5% | **8/8** |
| `combustion_degraded` | BSFC × 1.10 | +10.0% | **4/4** |
| `aggressive_driving` | 激烈度 1.75 + 目标车速 × 1.12 | +7.8% | 3/8 |
| `excessive_idling` | 额外怠速 620 秒 | +3.7% | **4/4** |

> 激烈驾驶在卡车上刻意建模为**超速**（空气阻力 ∝ v²）而不是更大的加速度 ——
> 353 kW 的卡车本来也做不出比例更高的加速度，这是真实物理，不是简化。

真实车队没有这种故障标签，所以**第 3.2 节的查准率/查全率是仿真专有指标**，
真实场景只能用人工复核与维修工单回流来评估。
